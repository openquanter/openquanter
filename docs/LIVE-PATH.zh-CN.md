# 实盘路径

`oq-gateway` 如何把交易所账户接到确定性内核上，以及为什么是这个形状。

**先写设计再写代码**，理由来自下面的调研：这个领域里每一个项目都是先做订单路径、
后补对账，而每一个都因此带着同一类 bug。

## 这份设计依赖的前提

内核是 `apply(State, Event) -> Outputs`，没有时钟、没有随机数、没有 I/O。回测与
实盘因此只差"谁生产事件"。这个前提不是假设——它已经付过账了：同一个内核在两年
的参考运行上逐笔重现。

所以实盘路径不是一套交易系统。它是**事件生产、持久化，以及一件文件永远测不到的
事：账户的模型是否与账户本身一致。**

## 调研发现了什么

详细读了四套系统（Hummingbot、hftbacktest、Barter-rs，以及三者共同的 FIX 祖源），
其中两条结论对本文档的影响最大。

**第一：钱是在"not found"上流走的。** Hummingbot 的创始事故值得原文引用，因为
它正是一个朴素对账器自己就会产出的东西：

> Binance API 有可能返回 order not found 错误……Hummingbot 于是再创建一单去替代
> 它。而旧单还活在 Binance 上，新单其实是重复单……这些重复单会不断累积，直到耗尽
> 交易者的可用余额。

机制是：一个**通用异常处理器**得出了"这单不存在"的结论。Barter 通过完全不同的
路径抵达同一个失败——它为一个可能还活着的订单**合成一个 `Timeout` 非活跃状态
事件**，然后把它删掉。两个代码库、无共享代码、同一个 bug。

**第二：调研中没有任何一个项目既记录实盘事件、又重放它们。** hftbacktest 的回测
完全确定性，实盘**零日志**。Barter 有一条带序号缺口检测的审计流，但从不持久化。
NautilusTrader 确实带了一个真正的事件存储——redb 后端、逐条哈希、立即持久化提交
——而它自己的文档写明这**不是**实盘重启路径：*"实盘重启仍然走快照加对账。"*
确定性被广泛宣称，而只在回测里实现。

还有第三条，它决定了对推进节奏的预期。Nautilus 的发布历史中有 **195 条对账相关
条目**，横跨约一百个版本，而且规律一致：在途检查带来了重查风暴与过早终态化；推断
成交带来了幽灵持仓、重复计数、零价成交与不确定 id；持续挂单检查带来了假
not-found 与幽灵撤单。**每一个为填补缺口而加的能力，都开启了一类新 bug。** 那个
项目里每一个配置开关都是一道疤。**这不是一个能一次设计对、然后就能用的系统。**

## 决策

### L1 — 对账先于下单存在，不是之后

读路径先交付，对着真实账户跑数周，之后才谈交易。这不是为谨慎而谨慎：对账器是
**唯一**能对回测触及不到的部分产出证据的组件，而且它产出这些证据的风险是零。

它同时把调研发现的那个失败顺序倒了过来。先做订单，意味着**带着钱去发现对账的
bug**——而那正是上面那段历史。

### L2 — "什么是真相"的三个答案，以及我们的

调研发现了三种互不兼容的策略：

| | 做法 | 代价 |
|---|---|---|
| hftbacktest | 每次连上就全撤单 + 重取持仓 | 不可能不一致。但每次网络抖动都毁掉整个挂单簿 |
| Hummingbot | 只轮询自己已知的订单 | 便宜。孤儿单永远发现不了 |
| Barter | 按 client id 合并交易所快照 | 架构干净。**静默错误**——它自己的文档说快照是*替换*，代码却是*合并* |

还有第四种，而且比这三种都好。Roq 把每一个已知订单标记为 stale，用交易所报告
覆盖，然后把**仍然是 stale 的**发出来——按构造，那就是交易所拒绝报告的订单，
因而是**终态但不可知**的。它**只发一次**，这让它成为一个边沿触发的告警而不是
一个需要有人记得去轮询的电平，而且 API **拒绝为它伪造终态**。它们的文档很诚实地
说明了原因：

> 由于我们无法知道断线期间订单是完成了还是被撤了，必须用其他手段来同步例如持仓
> ……最终方案可能需要在看到 stale 订单更新时由人工介入。

最后那句话才是正确答案，而上面三个项目都去找了一个自动的答案。

**我们采用 Roq 的：标记 stale → 用交易所答案覆盖 → 把残留当作一个需要被解决的
事实，而不是一个可以被发明的状态。** 任何本地有而交易所没有的东西都会被显式暴露
——绝不静默丢弃（那是 Barter 的幽灵单泄漏），也绝不假定它还活着（那是 Hummingbot
的孤儿单）。

快照还需要一个**终止符**。Roq 用 `DownloadBegin`/`DownloadEnd` 把下载括起来，这
就是 FIX 的 `LastRptRequested` 换了个名字：客户端必须知道快照**已完整**才能开始
做差集，否则它会拿一个残缺的答案去比，然后得出"所有还没收到的都消失了"的结论。

**持仓尤其是取回来的，不是推算出来的。** Barter 的快照里根本没有持仓字段，所以
漏掉的成交永远不可见。折叠成交是**预测**持仓的方式；问交易所是**知道**持仓的
方式——而两者之差，正是我们要的信号。

### L3 — 不一致就停机，绝不用发明来修复

**启动时，无条件**：对账失败意味着策略不启动。NautilusTrader 正是这么做的，而且
很明确——内核在 `trader.start()` 之前就返回了，而且有一条发布记录专门修复了
"对账失败后启动仍然继续"的路径。这也是 1.x 系统一直遵守的规则。

**运行时，两个最强的项目意见相左**，这个分歧值得如实记录，而不是按偏好抹平。

**NautilusTrader 选择修复。** 遇到持仓缺口，它**伪造一笔成交**——或者一整张
合成的 FILLED 订单——价格走一个四级回退：从"解出能重现交易所均价的那个价格"
开始，到"如果完全没有价格数据就下市价单"结束。它自己的代码注释承认了代价：
*"如果达到该状态经历了多笔成交，现在可能有一些信息损失。"* 重试预算用尽后它
放弃、记一条 error，**然后继续用它刚刚宣布无法对账的状态交易。**

**Roq 拒绝。** 它把残留作为 stale 只发一次，并且明说人工介入可能是唯一正确的
响应。

**我们跟 Roq**，理由和这里跑的东西直接相关：马丁格尔的补仓阶梯**锚定在持仓均价
上**。持仓错任何一点，得到的不是"略微偏差的阶梯"——而是**价位全错的阶梯，和一个
永远够不到的止盈**。伪造一笔成交来填缺口，就是在伪造这个锚点。

所以：短暂的订单级差异靠重查解决，而**持续的持仓分歧停机**，不是被放弃掉然后
继续交易。Nautilus 采取的那个中间选项——记录错误、继续运行——是我们不能用的。

至于为什么根本不选自我修复：**一个静默修复的对账器，无法告诉你它已经把同一个
差异每十秒修一次、修了一整周**。差异本身就是发现。Hummingbot 的 issue 列表展示了
另一条路的形状：**"balance mismatch" 和 "position mismatch" 的 issue 数量为零——
不是因为它从未发生，而是因为没有任何机制检测它，所以连描述它的词汇都不存在。**

### L4 — 订单 id 必须可重新构造

Binance 对 `newClientOrderId` 的唯一性规则是 *"在**未平**订单中唯一"*——作用域
是当前挂单集合，不是账户生命周期。订单一旦关闭，它的 id 可以被复用且不会被拒。
**它不是一个幂等令牌。**

调研的三个项目全部用**墙钟 + 进程号**生成 id。这在构造上就是反幂等的：崩溃之后
你无法向交易所问"我那单落地了吗"，因为**你无法重新生成那个要问的 id**。

我们的 id 由内核已经持有的状态派生——合约、腿、阶梯档位、序号——所以同一个意图
永远产出同一个 id，恢复时可以拿它去问。跨复用的唯一性由我们自建的去重存储保证，
因为交易所不提供。

### L5 — 意图先落 journal，再发出去

journal 本来就在内核前面（`D2`）。订单路径把这条延伸到网络边界：**发送意图在
socket 写之前就已持久化。**

Hummingbot 在订单**事件**处理器里做状态快照，所以 POST 到 ACK 之间那个窗口
——唯一要紧的那个窗口——是无保护的。在那里崩溃，订单活在交易所上而本地永久没有
记录。那是机会性快照；这是预写日志，**区别在于写发生在网络调用的哪一侧。**

### L6 — 终态需要两个通道都同意

REST 和用户数据流都会报告订单已结束，而两者之间没有顺序保证。**在第一份报告
到达时就擦除**，正是另一个通道的迟到消息复活一个死单、或丢掉一个活单的原因。

订单在**两个**通道都确认后才被擦除，策略**只被告知一次**，单通道确认的墓碑在超时
后回收。hftbacktest 是调研中唯一这么做的项目，而**每个项目都有这个问题**。

### L7 — 状态永不倒退

每一条入站更新都带一个等级和一个时间戳，会让状态机后退的更新被丢弃而不是应用。

FIX 早在 1990 年代就为此定义了 `OrdStatus` 的显式优先级序。Hummingbot 存了
`last_update_timestamp` 却从不读它：`current_state = order_update.new_state`，
无条件赋值。所以一条迟到的消息会让它的状态机倒退。

### L8 — 失败是三值的，"not found" 需要正面证据

调研中最强的单个想法，来自 NautilusTrader：

```rust
pub enum CommandFailure {
    /// 确定性的本地失败，证明命令从未被发出。
    /// 对这种证据，发一个终态拒绝事件是合法的。
    NotSent(String),
    /// 交易所侧结果未定义，命令可能已经被执行。
    /// 对这种证据，终态事件永远不合法。
    Ambiguous(String),
    /// 交易所明确声明该命令被拒绝。
    VenueRejected(String),
}
```

以及让它成立的那个区分：*"这个轴与可重试性无关。可重试性回答的是要不要再发一次；
这个回答的是交易所是否可能已经对第一次动过手。一个错误可以两者都是、只是其一、
或者都不是。"*

传输错误、超时、断连、重试耗尽、以及**发送之后**的解析失败，全部是 `Ambiguous`。
任何未分类的东西**默认是 `Ambiguous`**，而一个 ambiguous 的命令会保持在途，直到
流更新、查询或对账把它解决——**绝不从它制造出一个终态事件。**

全盘采纳，**包括它们的执行方式**：这是一条写成文档的**逐适配器合规要求**，不是
约定。一个把超时变成拒绝的适配器，会**测试失败**。

因此 "not found" 只能来自有类型的交易所响应。绝不来自通用异常，绝不来自本地超时，
也绝不来自对瞬时失败的计数。

Hummingbot 建了这个有类型的分类器，然后把它接到了错误的路径上：活跃订单上的
**任何**异常都路由到 `process_order_not_found`，于是**四次瞬时 HTTP 500 就会把
一个活着的、正常工作的订单向策略宣告为 FAILED**。而且它的计数是**累积而非连续**
的，所以一个长命订单会跨小时攒够假阳性。

没有被正面识别为"交易所说这单不存在"的失败，**默认视为瞬时**。计数是连续的，
任何一次成功都清零。

### L9 — 订单被隔离，绝不被遗忘

当必须停止跟踪时，订单进入一个隔离区，那里**继续轮询它、继续接受它的成交**，
而策略被告知它已经没了。

这是 Hummingbot 唯一一个毫无争议的好想法，而它们花了三年半、三次尝试才走到。
直接采纳。**"策略被告知什么"和"系统停止关注什么"是两个不同的问题，不能共用一个
答案。**

### L10 — 成交量取绝对值，不做累加

交易所报告累计成交量的地方，就用那个数。逐笔增量只用于费用和价格归因。

累加器需要一个逐 trade-id 的去重字典才能在重投递下保持正确；**快照在构造上就是
幂等的**。Binance 的 `ORDER_TRADE_UPDATE` 带累计值，所以没有理由去用那个脆弱的
形式。trade id 仍然要去重——重连后的重投递是常态，而 Barter 因为缺这个，持仓和
盈亏**双双重复计数**。

### L10b — 去重键按账户限定，且只在事后标记

一笔成交由 `(账户, 合约, trade_id)` 标识，**不是**只用 `trade_id`。交易所会
跨账户复用 trade id，Nautilus 有一条专门修复这个混淆的发布记录。

去重标记在成交**真正进入账本之后**才提交，不是在第一次看到它的时候。在接收时
就标记看起来等价，其实不是：如果这笔成交随后在下游被拒绝，那个标记会**永久压制
一笔从未被应用的成交**。Nautilus 在两个不同的 issue 号下修了两次。

### L11 — 断线就意味着不交易

只要有通道处于断开状态，策略就不能基于陈旧状态行动。Barter 无视
`connectivity == Reconnecting` 照常生成订单，而它唯一的断线钩子**默认是空实现**。

### L12 — 限流是闭环的

读取 `X-MBX-USED-WEIGHT`，遇 429 按退避处理，把 418 当作它本来的严重事件对待：
Binance 对屡犯者会升级到 *"2 分钟到 3 天"* 的 IP 封禁。Hummingbot 的限流器
**完全忽略这三个头**；另外两个项目根本没有限流。

### L13 — 时钟容差是不对称的，所以宁可跑慢

Binance 接受一个请求的条件是：

```
timestamp < serverTime + 1000 && serverTime - timestamp <= recvWindow
```

本地时钟**偏快**只有 1000 毫秒容差，**无论 `recvWindow` 设成多少**；偏慢则享受
完整窗口。所以偏移估计被**有意地偏向落后于交易所**，而且它以 RTT 中点、在单调
时钟基上计算，这样一次 NTP 跳变不会在传输途中损坏签名。

## 形状

```
        交易所 REST ─┐                    ┌─ 读：账户、持仓、
        用户数据流  ─┤                    │      挂单、成交
                     ▼                    ▼
              oq-gateway ──────────►  对账器  ──► 不一致则 FATAL
                     │                    ▲
        journal ◄────┤（意图，在 socket 之前）
                     ▼                    │
              sequencer ──► 内核 ──► 输出 ──► gateway（发送）
                                      │
                                观察者读 journal，永不进核
```

读和写在同一个 crate 里。曾考虑拆一个只读 crate——"这段代码物理上无法下单"这个
保证在结构层面更强——但被否决了：签名、错误分类和交易所的类型会**存在两份**，而
**两份可能不一致的请求签名实现，比一份带受审边界的实现风险更大**。边界改放在
类型层：读不需要交易能力，而能交易的那个类型必须显式构造。

## 这些东西怎么测

调研中每个项目的对账都是**只在实盘存在**的——*"回测里两边都由自己控制"*——这
意味着上面整套机制**没有被我们花了几个月验证的那个东西测到**。两个答案，都取自
调研：

**打乱、重复、丢弃的属性测试。** Nautilus 生成任意的成交与报告序列，做排列，然后
断言四条不变量在任何顺序下都成立：最终数量在精度内匹配交易所、均价在容差内匹配、
生成的成交保持未实现盈亏正确、合成 id 跨重放确定。它们的仓库里**签入了八个收缩
后的失败种子**——fuzzer 找到的真实 bug，永久钉住。

**逐适配器的书面合规套件。** Nautilus 那份有 2,279 行、约一百个用例，每个都规定
了前置条件、动作、期望事件序列和通过标准。**歧义类用例是关键的那些**：把超时变成
拒绝的适配器会失败。

这两样都比另一个选择便宜——那个选择是从上面那段发布历史里重新发现同样的事情。

## 顺序

1. **读路径 + 对账器。** 对着真实账户跑，什么都不改，只报告不一致。**先跑数周，
   再谈其他。**
2. **用户数据流 → 事件。** 仍然不下单：消费这条流、落 journal、折叠成一个模型，
   而对账器持续拿它与交易所比对。**一笔漏掉或重复的成交会表现为持仓分歧**——那
   正是要紧的那个测试。
3. **订单路径。** 发送前落盘、可重构造的 id、去重存储、双通道终态。
4. **风控门。** 放在内核**内部**（`D7`），这样它的决策是确定性的、进 journal 的、
   且被每一次回测演练到，而不是待在它本该守卫的那条路径旁边。
5. **装配与恢复。** 快照恢复、启动对账、平滑重启。

每一步在下一步存在之前就可测。**第一步尤其值得单独跑**，哪怕后面的东西一个都不
建：它本身就是对当前正在交易的系统的一个独立校验。

## 这份设计没有覆盖的

**余额。** Nautilus 对账订单、成交和持仓，把余额留给另一条路径，这里暂时也一样：
在持仓一致的前提下出现余额分歧，那是费用或资金费的记账问题，不是执行问题，而
回答它需要一个本设计还不具备的两侧模型。

**第二个交易所。** 这份设计是照着 Binance USDT-M 写的，因为那是在跑的东西。
`DownloadBegin`/`DownloadEnd`、三值失败分类和 staleness 差集都是与交易所无关的，
但这里没有任何东西在第二个交易所的"订单报告应该包含什么"的观念下被测过。

**以及：整份东西是设计，不是结果。** 上面那段关于 Nautilus 的 195 条对账记录，就是
诚实的预期：**这东西的第一版一定会在调研预测不到的地方出错**，而只读阶段的存在，
就是为了让出错这件事足够便宜。
