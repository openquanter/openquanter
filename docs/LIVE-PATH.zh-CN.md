# 实盘路径

[English](LIVE-PATH.md) · [中文](LIVE-PATH.zh-CN.md)

`oq-gateway` 如何把交易所账户接到确定性内核上，以及为什么是这个形状。

**先写设计再写代码**，理由来自下面的调研：这个领域里每一个项目都是先做订单路径、
后补对账，而每一个都因此带着同一类 bug。

## 这份设计依赖的前提

内核是 `apply(State, Event) -> Outputs`，没有时钟、没有随机数、没有 I/O。回测与
实盘因此只差"谁生产事件"。这个前提不是假设——它已经付过账了：同一个内核在两年
的参考运行上逐笔重现。

所以实盘路径不是一套交易系统。它是**事件生产、持久化，以及一件文件永远测不到的
事：账户的模型是否与账户本身一致。**

## 调研发现了什么

详细读了四套系统（Hummingbot、hftbacktest、Barter-rs，以及三者共同的 FIX 祖源），
其中两条结论对本文档的影响最大。

**第一：钱是在"not found"上流走的。** Hummingbot 的创始事故值得原文引用，因为
它正是一个朴素对账器自己就会产出的东西：

> Binance API 有可能返回 order not found 错误……Hummingbot 于是再创建一单去替代
> 它。而旧单还活在 Binance 上，新单其实是重复单……这些重复单会不断累积，直到耗尽
> 交易者的可用余额。

机制是：一个**通用异常处理器**得出了"这单不存在"的结论。Barter 通过完全不同的
路径抵达同一个失败——它为一个可能还活着的订单**合成一个 `Timeout` 非活跃状态
事件**，然后把它删掉。两个代码库、无共享代码、同一个 bug。

**第二：调研中没有任何一个项目既记录实盘事件、又重放它们。** hftbacktest 的回测
完全确定性，实盘**零日志**。Barter 有一条带序号缺口检测的审计流，但从不持久化。
NautilusTrader 确实带了一个真正的事件存储——redb 后端、逐条哈希、立即持久化提交
——而它自己的文档写明这**不是**实盘重启路径：*"实盘重启仍然走快照加对账。"*
确定性被广泛宣称，而只在回测里实现。

还有第三条，它决定了对推进节奏的预期。Nautilus 的发布历史中有 **195 条对账相关
条目**，横跨约一百个版本，而且规律一致：在途检查带来了重查风暴与过早终态化；推断
成交带来了幽灵持仓、重复计数、零价成交与不确定 id；持续挂单检查带来了假
not-found 与幽灵撤单。**每一个为填补缺口而加的能力，都开启了一类新 bug。** 那个
项目里每一个配置开关都是一道疤。**这不是一个能一次设计对、然后就能用的系统。**

## 决策

### L1 — 对账先于下单存在，不是之后

读路径先交付，对着真实账户跑数周，之后才谈交易。这不是为谨慎而谨慎：对账器是
**唯一**能对回测触及不到的部分产出证据的组件，而且它产出这些证据的风险是零。

它同时把调研发现的那个失败顺序倒了过来。先做订单，意味着**带着钱去发现对账的
bug**——而那正是上面那段历史。

### L2 — "什么是真相"的三个答案，以及我们的

调研发现了三种互不兼容的策略：

| | 做法 | 代价 |
|---|---|---|
| hftbacktest | 每次连上就全撤单 + 重取持仓 | 不可能不一致。但每次网络抖动都毁掉整个挂单簿 |
| Hummingbot | 只轮询自己已知的订单 | 便宜。孤儿单永远发现不了 |
| Barter | 按 client id 合并交易所快照 | 架构干净。**静默错误**——它自己的文档说快照是*替换*，代码却是*合并* |

还有第四种，而且比这三种都好。Roq 把每一个已知订单标记为 stale，用交易所报告
覆盖，然后把**仍然是 stale 的**发出来——按构造，那就是交易所拒绝报告的订单，
因而是**终态但不可知**的。它**只发一次**，这让它成为一个边沿触发的告警而不是
一个需要有人记得去轮询的电平，而且 API **拒绝为它伪造终态**。它们的文档很诚实地
说明了原因：

> 由于我们无法知道断线期间订单是完成了还是被撤了，必须用其他手段来同步例如持仓
> ……最终方案可能需要在看到 stale 订单更新时由人工介入。

最后那句话才是正确答案，而上面三个项目都去找了一个自动的答案。

**我们采用 Roq 的：标记 stale → 用交易所答案覆盖 → 把残留当作一个需要被解决的
事实，而不是一个可以被发明的状态。** 任何本地有而交易所没有的东西都会被显式暴露
——绝不静默丢弃（那是 Barter 的幽灵单泄漏），也绝不假定它还活着（那是 Hummingbot
的孤儿单）。

快照还需要一个**终止符**。Roq 用 `DownloadBegin`/`DownloadEnd` 把下载括起来，这
就是 FIX 的 `LastRptRequested` 换了个名字：客户端必须知道快照**已完整**才能开始
做差集，否则它会拿一个残缺的答案去比，然后得出"所有还没收到的都消失了"的结论。

**持仓尤其是取回来的，不是推算出来的。** Barter 的快照里根本没有持仓字段，所以
漏掉的成交永远不可见。折叠成交是**预测**持仓的方式；问交易所是**知道**持仓的
方式——而两者之差，正是我们要的信号。

### L3 — 不一致就停机，绝不用发明来修复

**启动时，无条件**：对账失败意味着策略不启动。NautilusTrader 正是这么做的，而且
很明确——内核在 `trader.start()` 之前就返回了，而且有一条发布记录专门修复了
"对账失败后启动仍然继续"的路径。这也是 1.x 系统一直遵守的规则。

**运行时，两个最强的项目意见相左**，这个分歧值得如实记录，而不是按偏好抹平。

**NautilusTrader 选择修复。** 遇到持仓缺口，它**伪造一笔成交**——或者一整张
合成的 FILLED 订单——价格走一个四级回退：从"解出能重现交易所均价的那个价格"
开始，到"如果完全没有价格数据就下市价单"结束。它自己的代码注释承认了代价：
*"如果达到该状态经历了多笔成交，现在可能有一些信息损失。"* 重试预算用尽后它
放弃、记一条 error，**然后继续用它刚刚宣布无法对账的状态交易。**

**Roq 拒绝。** 它把残留作为 stale 只发一次，并且明说人工介入可能是唯一正确的
响应。

**我们跟 Roq**，理由和这里跑的东西直接相关：马丁格尔的补仓阶梯**锚定在持仓均价
上**。持仓错任何一点，得到的不是"略微偏差的阶梯"——而是**价位全错的阶梯，和一个
永远够不到的止盈**。伪造一笔成交来填缺口，就是在伪造这个锚点。

所以：短暂的订单级差异靠重查解决，而**持续的持仓分歧停机**，不是被放弃掉然后
继续交易。Nautilus 采取的那个中间选项——记录错误、继续运行——是我们不能用的。

重查的意思是：对本进程仍认为在挂的订单，向交易所要它**自己的记录**——订单状态和
它的逐笔成交，带交易所的成交 id——把推送流没送到的部分，走和推送回报完全相同的路径
入账。这不是修复：不定价、不发明任何东西，成交 id 会把推送流已经送到的部分去重掉。
之所以需要它，是因为断开的推送流不会重放它错过的内容；重连期间成交的止盈单，否则就
是一个没有任何东西能解释的差异，进程会为了两次请求就能查到的一笔成交而停机。交易所
记录也解释不了的差异，仍然停机。

停机时撤掉会**增加**持仓的挂单，保留会减少持仓的挂单。什么都不撤，补仓阶梯会在一个
已经看不见它的进程底下继续成交；全部撤掉，持仓就没有了出场单。

至于为什么根本不选自我修复：**一个静默修复的对账器，无法告诉你它已经把同一个
差异每十秒修一次、修了一整周**。差异本身就是发现。Hummingbot 的 issue 列表展示了
另一条路的形状：**"balance mismatch" 和 "position mismatch" 的 issue 数量为零——
不是因为它从未发生，而是因为没有任何机制检测它，所以连描述它的词汇都不存在。**

### L4 — 订单 id 必须可重新构造

Binance 对 `newClientOrderId` 的唯一性规则是 *"在**未平**订单中唯一"*——作用域
是当前挂单集合，不是账户生命周期。订单一旦关闭，它的 id 可以被复用且不会被拒。
**它不是一个幂等令牌。**

调研的三个项目全部用**墙钟 + 进程号**生成 id。这在构造上就是反幂等的：崩溃之后
你无法向交易所问"我那单落地了吗"，因为**你无法重新生成那个要问的 id**。

我们的 id 由 `broker::IdScheme::compose` 组装：一个可选的、交易所签发的 broker 代码，
本进程的归属前缀，以及一个序号。序号取自会话能发单之前就**持久化预留**的一段区间
（`oq-live` 的 `order_ids.rs`），所以重启永远不会把同一个 id 分配两次——崩溃只会烧掉
没用上的 id；而 id 在订单发出之前就落进 journal（L5），所以恢复时能把它读回来、拿它
去问交易所。跨复用的唯一性因此来自我们自己的记录，因为交易所不提供。

### L5 — 意图先落 journal，再发出去

journal 本来就在内核前面（`D2`）。订单路径把这条延伸到网络边界：**发送意图在
socket 写之前就已持久化。**

Hummingbot 在订单**事件**处理器里做状态快照，所以 POST 到 ACK 之间那个窗口
——唯一要紧的那个窗口——是无保护的。在那里崩溃，订单活在交易所上而本地永久没有
记录。那是机会性快照；这是预写日志，**区别在于写发生在网络调用的哪一侧。**

这里的"持久化"指 fsync。每一条决策——下单、撤单、成交、对账——在 session 据此行动之前
就已落到设备上。观测（每个聚合窗口一条 tick、等待心跳）立即交给操作系统，随下一条决策的
fsync 一起落盘：断电最多让回放少最后几个 tick，不会丢一张订单。

### L6 — 终态需要两个通道都同意

REST 和用户数据流都会报告订单已结束，而两者之间没有顺序保证。**在第一份报告
到达时就擦除**，正是另一个通道的迟到消息复活一个死单、或丢掉一个活单的原因。

订单在**两个**通道都确认后才被擦除，策略**只被告知一次**，单通道确认的墓碑在超时
后回收。hftbacktest 是调研中唯一这么做的项目，而**每个项目都有这个问题**。

### L7 — 状态永不倒退

每一条入站更新都带一个等级和一个时间戳，会让状态机后退的更新被丢弃而不是应用。

FIX 早在 1990 年代就为此定义了 `OrdStatus` 的显式优先级序。Hummingbot 存了
`last_update_timestamp` 却从不读它：`current_state = order_update.new_state`，
无条件赋值。所以一条迟到的消息会让它的状态机倒退。

### L8 — 失败是三值的，"not found" 需要正面证据

调研中最强的单个想法，来自 NautilusTrader：

```rust
pub enum CommandFailure {
    /// 确定性的本地失败，证明命令从未被发出。
    /// 对这种证据，发一个终态拒绝事件是合法的。
    NotSent(String),
    /// 交易所侧结果未定义，命令可能已经被执行。
    /// 对这种证据，终态事件永远不合法。
    Ambiguous(String),
    /// 交易所明确声明该命令被拒绝。
    VenueRejected(String),
}
```

以及让它成立的那个区分：*"这个轴与可重试性无关。可重试性回答的是要不要再发一次；
这个回答的是交易所是否可能已经对第一次动过手。一个错误可以两者都是、只是其一、
或者都不是。"*

传输错误、超时、断连、重试耗尽、以及**发送之后**的解析失败，全部是 `Ambiguous`。
任何未分类的东西**默认是 `Ambiguous`**，而一个 ambiguous 的命令会保持在途，直到
流更新、查询或对账把它解决——**绝不从它制造出一个终态事件。**

全盘采纳，**包括它们的执行方式**：这是一条写成文档的**逐适配器合规要求**，不是
约定。一个把超时变成拒绝的适配器，会**测试失败**。

因此 "not found" 只能来自有类型的交易所响应。绝不来自通用异常，绝不来自本地超时，
也绝不来自对瞬时失败的计数。

Hummingbot 建了这个有类型的分类器，然后把它接到了错误的路径上：活跃订单上的
**任何**异常都路由到 `process_order_not_found`，于是**四次瞬时 HTTP 500 就会把
一个活着的、正常工作的订单向策略宣告为 FAILED**。而且它的计数是**累积而非连续**
的，所以一个长命订单会跨小时攒够假阳性。

没有被正面识别为"交易所说这单不存在"的失败，**默认视为瞬时**。计数是连续的，
任何一次成功都清零。

### L9 — 订单被隔离，绝不被遗忘

当必须停止跟踪时，订单进入一个隔离区，那里**继续轮询它、继续接受它的成交**，
而策略被告知它已经没了。

这是 Hummingbot 唯一一个毫无争议的好想法，而它们花了三年半、三次尝试才走到。
直接采纳。**"策略被告知什么"和"系统停止关注什么"是两个不同的问题，不能共用一个
答案。**

*现状：已采纳，未实现。* 代码里没有隔离区。`oq-live` 的 `unanswered` 队列是另一回事——
它跟踪的是提交后没有得到应答的订单——停止跟踪后不会继续关注那张单。

### L10 — 成交量取绝对值，不做累加

交易所报告累计成交量的地方，就用那个数。逐笔增量只用于费用和价格归因。

累加器需要一个逐 trade-id 的去重字典才能在重投递下保持正确；**快照在构造上就是
幂等的**。Binance 的 `ORDER_TRADE_UPDATE` 带累计值，所以没有理由去用那个脆弱的
形式。trade id 仍然要去重——重连后的重投递是常态，而 Barter 因为缺这个，持仓和
盈亏**双双重复计数**。

### L10b — 去重键按账户限定，且只在事后标记

一笔成交由 `(账户, 合约, trade_id)` 标识，**不是**只用 `trade_id`。交易所会
跨账户复用 trade id，Nautilus 有一条专门修复这个混淆的发布记录。

去重标记在成交**真正进入账本之后**才提交，不是在第一次看到它的时候。在接收时
就标记看起来等价，其实不是：如果这笔成交随后在下游被拒绝，那个标记会**永久压制
一笔从未被应用的成交**。Nautilus 在两个不同的 issue 号下修了两次。

### L11 — 断线就意味着不交易

只要有通道处于断开状态，策略就不能基于陈旧状态行动。Barter 无视
`connectivity == Reconnecting` 照常生成订单，而它唯一的断线钩子**默认是空实现**。

### L12 — 限流是闭环的

读取 `X-MBX-USED-WEIGHT`，遇 429 按退避处理，把 418 当作它本来的严重事件对待：
Binance 对屡犯者会升级到 *"2 分钟到 3 天"* 的 IP 封禁。Hummingbot 的限流器
**完全忽略这三个头**；另外两个项目根本没有限流。

*现状：部分实现。* 429 按 `Retry-After` 冷却、418 有退避；`X-MBX-USED-WEIGHT-1M`
从每个响应（包括被拒的响应）读取，并在 `oq-trade` 的 `status` 应答中以 `request_weight`
给出——Binance 与 Aster 共用一张表，两家都生效。它还没有用于节流：环路仍是开的，
真正拦住请求的仍是 429。

### L13 — 时钟容差是不对称的，所以宁可跑慢

Binance 接受一个请求的条件是：

```
timestamp < serverTime + 1000 && serverTime - timestamp <= recvWindow
```

本地时钟**偏快**只有 1000 毫秒容差，**无论 `recvWindow` 设成多少**；偏慢则享受
完整窗口。所以偏移估计被**有意地偏向落后于交易所**，而且它以 RTT 中点、在单调
时钟基上计算，这样一次 NTP 跳变不会在传输途中损坏签名。

## 形状

```
        交易所 REST ─┐                    ┌─ 读：账户、持仓、
        用户数据流  ─┤                    │      挂单、成交
                     ▼                    ▼
              oq-gateway ──────────►  对账器  ──► 不一致则 FATAL
                     │                    ▲
        journal ◄────┤（意图，在 socket 之前）
                     ▼                    │
              sequencer ──► 内核 ──► 输出 ──► gateway（发送）
                                      │
                                观察者读 journal，永不进核
```

读和写在同一个 crate 里。曾考虑拆一个只读 crate——"这段代码物理上无法下单"这个
保证在结构层面更强——但被否决了：签名、错误分类和交易所的类型会**存在两份**，而
**两份可能不一致的请求签名实现，比一份带受审边界的实现风险更大**。边界改放在
类型层：读不需要交易能力，而能交易的那个类型必须显式构造。

## 这些东西怎么测

调研中每个项目的对账都是**只在实盘存在**的——*"回测里两边都由自己控制"*——这
意味着上面整套机制**没有被我们花了几个月验证的那个东西测到**。两个答案，都取自
调研：

**打乱、重复、丢弃的属性测试。** Nautilus 生成任意的成交与报告序列，做排列，然后
断言四条不变量在任何顺序下都成立：最终数量在精度内匹配交易所、均价在容差内匹配、
生成的成交保持未实现盈亏正确、合成 id 跨重放确定。它们的仓库里**签入了八个收缩
后的失败种子**——fuzzer 找到的真实 bug，永久钉住。

**逐适配器的书面合规套件。** Nautilus 那份有 2,279 行、约一百个用例，每个都规定
了前置条件、动作、期望事件序列和通过标准。**歧义类用例是关键的那些**：把超时变成
拒绝的适配器会失败。

这两样都比另一个选择便宜——那个选择是从上面那段发布历史里重新发现同样的事情。

## 第一次实盘运行观测到了什么

读取器对着一个真实账户跑了八小时，一单未下。这里记六条，因为每一条都关系到某个
在此之前只能靠别人的发布说明来支撑的决策。

**七张单在同一毫秒离开挂单簿：一张成交，六张被撤销。** 持仓平掉，它身后那排挂着
的阶梯被整批撤回，而交易所报告七张的已成交量**全是零**——从快照无从分辨。全标成
"成交"，错六次；全标成"撤单"，只错一次，可**错的那次正是唯一动了钱的那笔**：它会
漏掉成交，同时把一个已经不存在的持仓报告成仍然开着，而这正是 L3 要拒绝的状态。同
一次运行中更早的一刻还有两张单一起离场，一成交一撤销替换，**两种猜法在同一瞬间各
错一半**。L2 和 L6 要求只报告离场、拒绝给出原因。那原本是借来的谨慎；现在它是唯一
不构成捏造的答案。

**轮询看不见成交，只看得见成交的后果。** 那张成交的单是在两次读取之间成交的。它
从未被观测到部分成交，也从未被观测到终态——先是挂着，然后就没了，持仓变了。成交
发生在何时、什么价格、分成几笔，这些**只存在于流里**。L6 论证过这件事，这次运行
把它演示了出来。

**残缺读取是常态，不是异象。** 一百二十四次读取里有四次少了某个部分，每次少的还
不是同一个。接下来的两千三百次全都完整。**"这是一次事件而非一个速率"本身就是发现**：
如果真有稳定的百分之三，就该做退避，而证据并不支持。那四次一次都没有被拿去比对，
所以一次都没有报出"订单消失"这种并未发生的事。

**余额动了，而其他什么都没动。** 在一个资金费结算边界上，没有成交、没有订单变化、
没有持仓变化，账户被扣了钱。**只比对持仓和订单的对账，对这一整类事件是瞎的**——而
这一类涵盖了所有不由策略引起的费用、结算与划转。

**交易所报告的持仓均价与推算的混合值精确相等**——在一个刚刚翻倍的持仓上，精确到
浮点数的最后一位。这个计算此前只和"同一意图的另一个实现"对过，从未和交易所对过。

**门在一次根本没发生的读取上报告了成功。** 单次模式在读取残缺时退出零，而单次正是
启动门用的模式：它会对着一个自己没看见过的账户报告"相符"。这是 **L8 的形状**——既
非通过也非失败的第三种结果——出现在一个没有套用 L8 的地方。现在它单独退出。这个
缺陷来自把东西跑起来，不是来自把它读一遍。

## 顺序

1. **读路径 + 对账器。** 对着真实账户跑，什么都不改，只报告不一致。**先跑数周，
   再谈其他。**
2. **用户数据流 → 事件。** 仍然不下单：消费这条流、落 journal、折叠成一个模型，
   而对账器持续拿它与交易所比对。**一笔漏掉或重复的成交会表现为持仓分歧**——那
   正是要紧的那个测试。
3. **订单路径。** 发送前落盘、可重构造的 id、去重存储、双通道终态。
4. **风控门。** 计划放在内核**内部**（`D7`）。实际建成的是 `oq-risk`：实盘会话在
   每次发单前都要问它，检查通过时返回一张装着它所批准那张单的许可证。它不在内核里，
   回测也不链接它，所以它的决策**不会**被回测演练到。
5. **装配与恢复。** 快照恢复、启动对账、平滑重启。

每一步在下一步存在之前就可测。**第一步尤其值得单独跑**，哪怕后面的东西一个都不
建：它本身就是对当前正在交易的系统的一个独立校验。

## 这份设计没有覆盖的

**余额。** Nautilus 对账订单、成交和持仓，把余额留给另一条路径，这里暂时也一样：
在持仓一致的前提下出现余额分歧，那是费用或资金费的记账问题，不是执行问题。模
型本身已不再是障碍——`Fees` 带一个 maker 费率和一个 taker 费率，并允许 maker 一
侧为负；资金费结算进余额、又与余额分开记账，所以本地这一侧说得出它认为自己被
收了多少。缺的是那次比对，而它没被建起来的原因是：交易所那一侧的余额也会因为
执行模型看不见的事情而变动——划转、跨品种保证金、子账户移动。一笔能被其中任何
一项解释掉的分歧，都不构成关于执行的证据，这正是这里只对账那些构成证据的东西
的原因。

**第二个交易所——已经不是缺口了。** 这份设计是照着 Binance USDT-M 写的，因为当时
在跑的是它。现在 OKX 也有了账户读取和事件流，`oq-trade` 能交易 Binance、Aster 和
OKX；执行一致性测试套件用同一组用例驱动全部七个适配器。第二个交易所确实对"订单报告
应该包含什么"有不同看法——OKX 把拒单包在 200 里——而这正是那套测试要抓的东西。

**这份东西先是设计，然后才是结果。** 上面那段关于 Nautilus 的 195 条对账记录，仍然
是诚实的预期：**这东西的第一版一定会在调研预测不到的地方出错**。现在它还能在没有
交易所的情况下被端到端地演练：`oq_live::sim` 让整个实盘进程对着一个带 seed、可以被
要求出错的模拟交易所运行，`tests/dst.rs` 要求同一个 seed 产出同一次运行。

## 已记录的账本证据

实盘记录命名空间追加两种编号，既有载荷不变：

| 编号 | 载荷 |
|---|---|
| `EXECUTION`（12） | 带长度的客户端 id、u32 小端内核载荷长度、标准 `Event::VenueFill` 载荷：完整双时钟、标的/订单/成交 id、方向、offset、流动性及费用证据 |
| `LEDGER_START`（13） | 观测时刻与标的 id（i64 小端）、价格/数量 scale（u8）、合约大小、price tick、qty step、最小名义额、每 tick-lot 现金价值与起始现金（i64 小端）、模式（0 单向、1 对冲） |

这些是**实盘记录编号**，不是内核事件编号。成交嵌入内核编码但不复用其外层 kind。
标的经济属性必须匹配所记录现金乘数。新生产者即使观测持仓列表为空也记录初始状态，
缺少证据不等于 flat。`Session::record_fill` 保留旧版无费用接口；`record_execution`
和 `record_ledger_start` 提供记账路径。缺失/不可读手续费不能退回模型的零费率，
`Fee::Reported(Cash::ZERO)` 才是已观测的零。

```bash
oq-replay session.oqj --ledger
oq-replay session.oqj --ledger --require-coverage
```

账本读取器选择最近 session，经权威实盘账本重放，拒绝缺失上下文/初始持仓、旧版无
费用成交、未知记录、重复经济身份与残缺尾部，打印已记录余额、已实现 P&L、费用、
资金费和持仓腿。退出 0 代表重放成功，不证明交易所全部现金流已捕获；未知费用退出 2，
`--require-coverage` 在缺少显式资金费覆盖证明时也退出 2。看到一个资金费金额不证明
没有漏结算。策略决策、保证金投影、划转、保险金调整都须有各自证据。旧文件须在独立
身份下补充证据，不能改写原文件来消除来源缺口。

实盘账本不依据模型 mark 合成强平成交或保险金转移，而是等待账户流确认平仓后才改变
实际库存。shadow/风控可投影强平，但投影不是交易所事件。

### shadow 的初始库存

runner 以同一份观测钱包、仓位模式、数量和入场基础启动 books 与 shadow。hedge 模式
保留双腿，即使 net 为零；one-way 模式拒绝双腿初态。`State::with_initial_legs` 直接
初始化成本基础，不伪造成交、手续费、已实现 P&L，也不按尚未观测的 mark 清算。
shadow 成交日志因此只有启动后的模型执行。初始基础精度仅限交易所快照提供的精度。
这个边界条件不重建历史经济记录或策略 warm-up 状态，也不能单独证明重启 parity 或
资金费/历史覆盖完整性。

等待费率或账单的资金费结算在 30 分钟 overdue 边界后仍保留。
`FundingWatch::unresolved` 暴露未解时间戳，`asking_since` 继续包含最早未解项。晚到
答复可入账一次。watch 内按稳定资金费账单 ID 去除重叠历史中的重复行；身份冲突或
将一个 ID 分配到两个结算窗口会保持归因不可用。这些检查不证明完整历史覆盖，也不
跨重启持久化 pending，更不重新发现从未进入调度的结算。

下一结算调度无法发现时，host 按相同的 60 秒资金费轮询重试，即使没有 pending 结算。
`FundingWatch::schedule_gaps` 按注入时间保留从发现失败到获得未来调度之间的区间；
不接受过时的下一结算时刻，也不外推交易所间隔。未来结算恢复捕获，但包含未知调度
区间的 run 仍保持归因不可用。这些区间目前保存在 watch 内；持久化历史/覆盖记录及
漏结算重建仍是独立的恢复工作。

Binance 资金费账单和费率读取器按包含时间边界的方式分页，按稳定身份去重，并拒绝
冲突证据。满页无法前进、后续请求失败、耗尽 50 页上限时均失败，不返回前缀冒充
成功。同时间边界不跳过：如果当前 cursor 无法枚举一个满毫秒内的全部记录，该区间
仍未解。读到最后一个短页不证明交易所保留了全部早期记录，也不建立持久化账户历史
覆盖证据。

新资金费结算使用追加的 `FUNDING_EVIDENCE`（14）。payload 先保存不变的 `FUNDING`
字段（接收 ns、结算 ms、长度前缀 rate/mark、venue/model cash、0/1 验证字节），
再存 i64 LE 非负行数及每条原始账单的 `(id, time_ms, amount)` 三个 i64 LE。解码拒绝
残缺行、非法数量/标志和尾随字节。行属于当前 session 的交易所/账户边界及账本 symbol。
重放检查精确合计，拒绝跨不同结算复用 ID，检查每行位于结算的 60 秒窗口，并报告
已识别行数，不把身份证据升级成历史覆盖证明。旧聚合资金费仍可读取，但没有 ID 可
验证；其 payload 不复用。

未知调度区间内，确认的资金费账单行可恢复交易所现金，而不重建未观测的模型仓位。
调度重新发现后仍从最早记录缺口继续轮询；费率不可用不阻断只读账单恢复路径。
匹配已知 pending 结算的行保留在其库存快照路径。已知结算与缺口恢复共享稳定 ID；
历史重送不重复入账，冲突保持显式。仅记录缺口内、不晚于接收时刻的行可恢复。这不
构成跨重启的完整账户历史恢复，也不宣称覆盖这些缺口之外的行。

`FUNDING_RECOVERED`（15）按 i64 LE 编码接收 ns、查询下/上界 ms、非负行数，然后
编码原始 `(id, time_ms, amount)` 三元组。它刻意没有模型金额字段。重放检查范围不
晚于接收、行位置及与 `FUNDING_EVIDENCE` 共享的重复 ID。`oq-replay --ledger` 报告
没有历史模型金额的资金费行数。恢复观测现金不修复归因、不证明覆盖，也不关闭 G12。

`FUNDING_STATE`（16）独立于现金持久化 watch 的变更义务。按 i64 LE 编码接收 ns、
pending 数量及时间戳，再编码 i64 LE 缺口数量；每个缺口含下界 ms、0/1 上界存在字节
及可选上界 ms，最后含 0/1 不确定性存在字节及可选长度前缀原因。分配内存前以剩余
payload 限制数量；拒绝非法标志和尾随字节。

session 在资金费捕获和轮询之后写状态，即使交易所未返回行。未变状态不产生重复
记录。原生重放验证时间边界和义务的单调性：pending 只有在已记录结算后才能消失，
已有缺口不能移除、已关闭边界不能改写，不确定性不能静默清除。关闭调度发现缺口不
解除历史覆盖义务。后续状态写入中断时，最终报告仍可从经济记录解除已答复 pending。
没有这个记录的旧 journal 义务未知。持久化使进程退出后的义务可检查；自动重启恢复
和完整覆盖证明仍是独立恢复工作。
