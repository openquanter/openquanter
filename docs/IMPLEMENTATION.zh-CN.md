# OpenQuanter — 实施方案

> 状态：**评审稿** · [English](IMPLEMENTATION.md)
> 配套文档：[需求规格说明](REQUIREMENTS.zh-CN.md) · [路线图](ROADMAP.zh-CN.md)

本文档说明架构、其背后的设计决策、crate 划分，以及交付需求的具体工程计划。
凡是有成熟先例的决策——无论来自开源系统、交易所基础设施还是学术文献——都会点明
先例，使后来的贡献者可以**评估**推理过程，而不是被动继承结论。

## 1. 架构

```
             ┌── 输入适配器 ───────────────────────────────────────────┐
             │  live: 交易所网关 │ backtest: 数据平面 │ sim: 场景生成器 │
             └───────────────────────────┬─────────────────────────────┘
                                         ▼
┌── Sequencer + Journal（oq-journal）─────────────────────────────────────────┐
│  所有事件先编号、先追加写入 mmap journal，再进入内核。journal 同时是：       │
│  审计流、重放源、恢复机制、进程间传输。读端容忍撕裂的尾部记录。             │
└───────────────────────────┬─────────────────────────────────────────────────┘
                            ▼
┌── 确定性内核（oq-core）—— 按标的分片，片内单线程 ───────────────────────────┐
│    fn apply(&mut State, Event) -> Outputs                                   │
│    内部禁止：读时钟 / 随机数 / I/O / 线程。时间是一种事件。                 │
│  ┌─────────────┐ ┌───────────┐ ┌───────────┐ ┌────────────────┐             │
│  │ 撮合        │ │ 保证金    │ │ RiskGate  │ │ 账本           │             │
│  │ oq-engine   │ │ oq-margin │ │ oq-risk   │ │ oq-types       │             │
│  │ L0…L3       │ │ 强平      │ │ 硬上限    │ │ typestate      │             │
│  └─────────────┘ └───────────┘ └───────────┘ └────────────────┘             │
└──────┬──────────────────────┬─────────────────────────┬─────────────────────┘
       ▼                      ▼                         ▼
┌─ 策略层 ───────────┐ ┌─ AI 层 ────────────────┐ ┌─ 输出适配器 ──────────────┐
│ Tier A: Rust trait │ │ oq-infer  （生产级）   │ │ live:     oq-gateway      │
│ Tier B: Python     │ │ oq-env    （RL，受控） │ │ backtest: 成交模拟回注    │
│  兼容 / 达速模式   │ │ oq-lab    （沙盒）     │ │ 观察者读 journal，永不进核│
└────────────────────┘ └────────────────────────┘ └───────────────────────────┘
┌─ 数据平面（oq-data）────────────────────────────────────────────────────────┐
│ Arrow/Parquet 双时戳 │ 双时间参考数据 │ 严格 as-of join                      │
│ oq-l2feed 采集工具   │ oq-features PIT 特征层                               │
└─────────────────────────────────────────────────────────────────────────────┘
```

这个形状导出三条值得明说的性质：

- **回测与实盘只差事件生产者。** 不存在一个需要与实盘引擎保持同步的独立回测引擎。
- **journal 是集成点。** 监控、分析、跨进程聚合都读 journal。除 sequencer 之外，
  没有任何东西能写回内核。
- **确定性不是测试便利，而是恢复机制。** 让 fuzzer 能复现故障的那条性质，也正是
  让崩溃进程能重建状态的那条性质。

## 2. 设计决策

### D1 — 纯确定性状态机内核

内核形如 `apply(State, Event) -> Outputs`，不持有任何环境权限。时间以
`TimeEvent` 进入。这是 LMAX/Aeron 谱系，现代交易框架各自独立收敛到了同一形态。

*推论：* 任何"这里顺手读一下时钟""这里顺手写个日志"都是设计违规，不是风格偏好。
lint 与评审强制它，重放测试兜住漏网的。

### D2 — Sequencer 与 journal 前置于内核

事件在内核观察到之前先编号、先持久追加。这与交易所与行情基础设施中的 tick 捕获
架构、以及同一谱系的内存映射队列库设计一致。

*推论：* 快照由流内事件触发（因此快照落在明确的序列号上）；读端必须容忍最后一条
撕裂记录；"到底发生了什么"永远不取决于日志级别配置。

### D3 — 分片单线程 + 环形缓冲

按标的分片、片内单线程、环形缓冲交接、预分配缓冲、热路径少分支。async 限定在
网关边缘。热路径排除工作窃取调度器，因为其尾延迟不可预测——而这正是 p99 目标
最无法容忍的。

### D4 — 保真度阶梯 + 正交保证金叠加层

执行真实度（L0–L3）与账户真实度（保证金层）是两个独立维度。L0 语义发布后冻结，
充当回归锚点。

`oq-margin` 是独立模块，而不是账户对象上的一个字段：分级维持保证金表按双时间
版本化（交易所会改规则，旧回测必须用旧规则）、逐 tick 占用与强平价、强平单像
普通订单一样进撮合、可注入的资金费尖峰场景。

撮合与保证金都是纯函数，并由属性测试覆盖：数量守恒、价格时间优先、无交叉盘、
保证金占用非负、强平价单调。交易所撮合引擎的形式化方法实践，是把这些当作
机器可检查的不变量（而非评审意见）的先例。

### D5 — 双时戳与固定布局事件

每条行情记录带 `exch_ts` 与 `local_ts`，纳秒精度。事件采用 `repr(C)` 零拷贝
布局。**字段永不复用**——一个字段跨版本改变含义，是电子交易史上代价最惨重的
若干事故背后的共同失效模式。

### D6 — 一核三环境

回测、沙盒、实盘只在适配器与时钟上有差别。这使"我测的策略就是我上的策略"成为
结构性性质，而不是靠纪律维持的习惯。

### D7 — 不可绕过的风控闸门；未知状态即致命

在策略输出与任何交易所之间设置管道级硬检查，外加 kill switch 与启动对账。若
对账无法确立真相，进程拒绝交易。股票市场的盘前风控监管要求编码的是同一原则，
而业内标志性的巨亏事故有着同一个根因：在状态未知时继续动作。

### D8 — 确定性红利：全系统仿真

因为内核是确定性的，随机化故障仿真器可以遍历调度、网络与交易所异常行为，并由
`(seed, commit)` 复现任何一次失败。分布式数据库中的故障注入仿真器是这里的范本。

场景语料以**通用**失败模式作为种子：乱序与重复的成交回报、撤单丢失、合成零价
成交、用户流僵死、重连风暴、时钟跳变、行情 gap。任何运营交易系统的人都会攒出
一份这样的清单；把它编码成可执行场景，就是把运维伤疤变成持久的测试资产。

### D9 — AI 按证据强度分层

- **推理（成熟）。** Python 训练，导出 ONNX 或编译梯度提升树，在 Rust 中运行，
  intra/inter-op 单线程、预热、固定形状。设 parity 门比对 Python 与 Rust 的预测，
  因为树模型的 float32 阈值处理在不同实现间会漂移，而这种漂移会静默地改变交易决策。

  **推理运行在内核之外，预测以 journal 事件的形式进入系统。** 见 D14——
  主要理由并不是确定性。
- **训练（受控）。** 控制反转的 gym 式环境 + 原生向量化批处理。以 L1 保真度为
  前置：在低保真环境训练会产出利用仿真器缺陷的策略。
- **探索（时间盒）。** LLM 沙盒，配类型化只读工具 API 与审计日志。仅用模型训练
  截止日之后的数据评估。模型输出是提案；硬限制留在引擎层。

### D10 — 数据层的 PIT 正确性

任何会追溯变更的数据（资金费时刻表、保证金分级、合约规格、上下架）双时间存储。
as-of join 默认严格 `<`，因为常见 dataframe 库的闭区间语义会把同时戳信息泄漏进
特征。一份特征代码同时服务研究与实盘，并用线上/线下一致性度量来证明它。

### D11 — 为 coding agent 设计的代码库

每个 crate 一份 200 行以内的 `AGENTS.md`，写明本地命令与不变量。分层验证锚
——单测 → 属性 → golden → parity——使 agent 或新贡献者无需把整个系统装进脑子
就能判断一次改动是否安全。golden 基线变更需要 PR 中的人工显式确认。

这同时也是 bus-factor 的缓解手段：这个领域的项目往往死于唯一维护者离开，而防线
是**写下来、可机器校验的行为**，而不是描述意图的文档。

### D12 — 运行拓扑与安全

- **每账户一进程。** 一个进程拥有一个账户、其策略与自己的 journal。故障域不重叠，
  一个账户的对账失败不会污染另一个。组合层视图由读 journal 构建，而不是共享
  交易状态。
- **凭证处理。** API key 永不出现在提交的配置中；从环境变量或 OS keyring 注入，
  且只存在于网关进程内存中；研究与回测进程没有访问路径。
- **时钟纪律。** 主机运行 NTP/chrony。采集进程在启动时记录时钟偏移估计并随数据
  归档——建立在未经校验的本机时钟之上的延迟建模，地基是歪的。

### D13 — 基线由内容标识，而不是由 commit 标识

只钉在代码 commit 上的回归基线会**静默失效**。输入数据被修正、某个配置默认值挪
了、数据集重新导出了——代码没动，于是基线看上去仍然有效，而下一次比对报出的
mismatch 根本不是回归。

这种失效模式比"漏掉一次回归"更糟：它给出的是一个**自信的错误答案**，读到它的人
无法区分"引擎变了"和"输入变了"，接下来的时间会花在二分一段根本没问题的代码上。

因此本项目中每一条 parity 与 golden 基线都由三元组标识：**(代码 commit、输入
数据内容哈希、生效配置哈希)**，比对工具必须对自己的输出做分类：

| 三元组状态 | 报告 |
|---|---|
| 三元全部一致 | 差异是**行为性**的——一次需要排查的回归 |
| 任一元不一致 | **`基线已失效——需 rebase`**，并指明是哪一元变了 |

对输入做哈希只花微秒级开销，却消除了一整类误诊。该规则同样适用于 golden 测试：
样例数据变了的 golden 基线是**过期**，不是**被违反**。

### D14 — 模型预测是事件，不是函数调用

推理运行在内核**之外**。一次预测产生后，提交给 sequencer、落 journal，然后才被
投递——和任何其他输入一样。内核里永远不会出现"调用模型"这件事。

确定性方面的理由是成立的，但它是次要的。**主要理由是：内核内的同步调用会美化
每一次回测。**

实盘中，预测总是**滞后于**产生它的那条行情：要算特征、要跑模型、结果要传回来。
而内联调用模型的回测，会把一个**零延迟的预测**交到策略手上，数据是市场刚刚才产生的。
这和"账户永远不会被强平"是同一类谎言——仿真悄悄赠送了一件现实世界不提供的东西。

做成事件之后，预测**天然晚于它所依据的数据**，回测与生产的时序一致，策略也就不可能
被建立在一个上线后并不存在的时间优势上。

由这个决策导出的后果：

- **重放永远不重新调用模型。** 它回放记录下来的预测。因此即使模型跨机器不确定、
  被重新训练过、甚至（远程大模型的情况）原理上就不可复现，过去那次运行依然精确重现。
  内核靠"不依赖外部世界保持稳定"来保住自己的保证。
- **内核保持整数运算。** 浮点结果在不同 CPU 上末位有差异；把推理放在外面，正是内核
  能维持 `i64` 定点、因而跨机器逐位一致的原因。
- **journal 里记录了模型当时到底说了什么。** "14:32:07 时模型预测了什么、输入是什么"
  变成事后可回答的问题——而这恰恰是事故复盘第一个要问的。
- **预测事件携带模型标识与输入特征的哈希**（沿用 D13）。这样才能区分"模型变了"和
  "特征变了"；没有它，一个不同的预测无法归因。
- **Python/Rust parity 门（G9）顺带就有了。** 用第二个推理实现重放同一份 journal，
  再用 `oq-parity` diff 预测事件即可，不需要另建一套装置。
- **只有一条代码路径。** 回测时推理组件运行并把预测事件写进 journal；生产时做同样的
  事。差别只在事件生产者——和这套设计里其他所有地方一样。

代价是热路径上多一次事件往返，以及 journal 变大。相对 100 µs 的 p99 预算，这次往返
付得起；journal 增长是容量规划问题，不是设计问题。付出这些换来的是**一个不会在
"策略何时知道某件事"上撒谎的回测**。

### D15 — 交易所是一个适配器，而它决定的事情之一是"一天是什么"

采集路径逐字节存储报文，只解析出足够把一条记录放进某个窗口的信息。交易所之间所有
不同的东西都放在一个 trait 后面：订阅哪些流、订阅如何被确认、报文长什么样、每个
品种的报价精度，以及**一条记录属于哪个归档窗口**。

最后这一条才是让它成为设计决策而非重构的原因。归档的核心不变式是**一个文件装一个
完整周期**——合并工具、订单簿校验、tick 转换器全都依赖它——而按 UTC 时钟切分只对
永不收盘的市场满足这个不变式。美股一个交易时段是 UTC 日里的 6.5 小时，其余是空的；
期货时段前一晚开盘、跨过午夜，时钟规则会把**一个交易日变成两个文件**，而下游每个
工具都继承这个割裂。框架不绑定资产类别，所以这个假设必须从归档核心里挪出来，放到
交易所那一侧——时段本来就属于市场。

**没有附带任何交易所日历。** 没有真实的交易所去校验，写出来的日历只能靠猜；而**错的
日历比没有日历更糟，因为它看起来权威**。现在存在的是接缝，加一个与既有行为完全一致
的默认实现。

同样的推理把"订阅"和"报文解析"也纳入了契约，两者各自源于一次真实的失败。一个不校验
流名就接受订阅的交易所，会确认一个已停用的流然后永远沉默——**这和安静的市场无法区分**，
所以契约里带上"订阅如何被确认"，超时无数据即为错误。为某个交易所写的报文解析器在另一
个交易所的数据里什么都找不到，返回空而不是报错——所以解析也归交易所，否则一份完全可读
的归档会转换出零条记录，并声称自己是空的。

### D16 —— Python 是一个绑定,不是一次妥协

反对 Python 层的理由是"它会稀释零依赖卖点"。**拿仓库实际强制的东西去核,这句话不成立**,
而它依赖的那个说法本项目从来没有做过。

`scripts/check-composability.sh` 的依赖预算是**按 crate 设的**:12 个为零,4 个为六十。
README 的声称也是相应地具体——**引擎**没有第三方依赖,凡是带依赖树的,都是必须和进程外
某样东西通信的那一类。`oq-l2feed` 带 TLS 栈是因为它要和交易所说话;一个绑定 crate 带
PyO3 是因为它要和 Python 说话。**两者都不改变那 12 个零**,而 CI 在每个 PR 上证明这一点,
不是请谁相信。

所以对 Python 该谨慎的原因不是依赖卫生,是另外三件,值得点名,因为它们才是真的有代价:

**Python 那层暴露的东西会变成 API。** 先暴露什么,用户就照着写什么,而且冻得最死。这是
"**早点暴露一个小面**"的理由,不是"一个都不暴露"的理由。

**分发不再是 `cargo build`。** 绑定以 wheel 分发,按平台、按解释器。截至 2026 年这意味着:
一个面向最低支持版本的 `abi3` wheel、一个给自由线程 3.14 的 `cp314t` 专版、以及 3.15
落地后的 `abi3t`——**PEP 803 已在 2026 年获批**,为自由线程构建定义了稳定 ABI。这是实打实
的工作量,但它属于构建基建,不属于架构。

**必须保住一条纯 Rust 的路。** 引擎要能在附近没有任何 Python 解释器的情况下构建和测试,
否则 **Rust 内核会悄悄变成某个 Python 库的实现细节**。依赖那一半已由 per-crate 预算强制,
剩下那一半由组合性检查里"每个 crate 单独构建"那一步强制。

最可比的项目也是这么解的:NautilusTrader 跑一个 Rust 内核 + PyO3 绑定 + Python 作控制面,
**同时保留一条完全不需要 Python 的纯 Rust 路径**。

**它取代了一条风险。** 登记表里"PyO3 回调开销主导 Python tier"那条是在**有全局解释器锁
的世界里**写的。PyO3 v0.28 支持自由线程 Python 3.14 与 GIL 释放 API,而一个管线里不持有
共享 Python 状态的模块可以标 `gil_used = false`,在自由线程解释器上运行而不重新启用锁。
开销问题现在是**可测量的**而不是结构性的——那是另一类风险,已按另一类记下。

**分期,以及分期的理由。** 那个更窄的提案——只暴露统计和保证金偏差报告,让 Python 用户
**评估他们现有的回测**而不是迁移过来——**保留,但不是作为全量绑定的替代品,而是它的第一期**。
它的价值不在于更安全,而在于**它是通往一个外部用户的最短路径**,而外部用户是 M3 四个准入
条件之一,也是唯一一个**买不到、只能等来**的。全量绑定随后。小面不排斥大面。

### D17 — 没有 MainEngine：装配在类型里，不在注册表里

从 1.x 那一系迁过来的人会先找一个 `MainEngine`——一个持有网关、应用、事件引擎、
数据库和 OMS 的中枢对象，各部分通过 `get_gateway(name)`、`add_app(obj)` 在运行时
互相取用。这里没有这个东西，而缺席是决定，不是遗漏。

**装配的位置是 `oq-live`**，它的职责写法和 MainEngine 不同：闸门决定一张单能不能
发，网关知道怎么发，流告诉发生了什么，**三者互相不认识**；这个 crate 是它们相遇
的地方，而"相遇"本身就是目的。`Session` 是**唯一能发出订单的路径**——顺序正确
不是靠调用者记得先检查，是靠没有别的路可走。

形状上的差别有四处，前三处是 Rust 的常规做法：

| | MainEngine | 这里 |
|---|---|---|
| 组合时机 | 运行时注册 `add_gateway(obj)` | 编译期泛型 `Session<E: Execution>` |
| 所有权 | 一个对象持有一切，各处取 `&mut` | 组件各自持有，消息移动所有权 |
| 通信 | 共享事件总线对象 | 通道，没有人"拥有"引擎 |
| 接线图 | 藏在注册顺序里 | 就是 `main` 的代码，读得到全部连接 |

前两处在 Rust 里不是风格问题：一个被所有子系统 `&mut` 的中枢会把你逼向
`Rc<RefCell<_>>` 或 `Arc<Mutex<_>>`，**用运行时 panic 和死锁换掉编译期错误**。

**第四处才是对本项目致命的那一处。** 一个谁都能伸手进去改的中枢，正是"这个状态
是谁改的"变得无法回答的地方；而内核的全部前提是状态只能由事件推动
（[D1](#d1--纯确定性状态机内核)）。只要存在"某个组件直接调中枢改了状态"这条路径，
它就不进 journal，重放就对不上，[归因](REQUIREMENTS.zh-CN.md#310-实盘差额归因--fr-attrib)
链就断了。**MainEngine 与"每一分差额都说得清"在结构上冲突**，这不是偏好。

**动态分发仍然用，但只用在该用的地方**：从配置决定这次连哪个交易所，是运行时的
问题，`Box<dyn Account>` 正合适。**"选哪一个"是运行时的，"图长什么样"是编译期
的**——MainEngine 的问题从来不是它用了动态分发，是它让整张图都变成了运行时可变。

这里的 trait 是 `Account` 而不是 `Execution`，理由值得记下来，因为第一版就是这么
错的。`Execution` 说的是"怎么把一笔单发出去"，而这不足以跑起来：在第一笔单之前，
还要对时、要拿到这个部署此刻发布的精度与最小变动、要问清持仓模式、要读余额和挂单，
还要开一条听回执的流。这些当初都直接落在具体的 `Binance` 上，散在 runner 里九处
——所以一个适配器可以把 `Execution` 实现得完完整整，却依然跑不起来。这正是发生过
的事：OKX 客户端写好了，用不了，而且**没有任何东西说得出它还欠什么**，因为缺的那
部分从来没有名字。

九处里有一处值得单独点名。runner 按 `IdRules::BINANCE` 这个编译进去的常量生成客户
端订单号——36 字符、允许标点；OKX 是 32 字符、纯字母数字。也就是说 OKX 适配器会在
提交那一刻被拒，**而策略此时已经决定要交易了**，被一条 runner 本来就不该有立场的
规则拒掉。

`Account` 就是这份清单，而且这份清单现在是可校验的：`oq-gateway` 里有一个测试用
交易所，只依赖 trait 本身实现。哪天有人加进一个只有 Binance 才实现得出的方法，它
会在那里当场编译不过，而不是半年后卡在某个人写了一半的适配器里。

行情侧刻意没有并进来——它自己有接缝 `oq_l2feed::Venue`，合并会让一个只做采集的工具
被迫持有账户凭据。两侧改用身份绑定：runner 用 `venue.id()` 开行情，账户侧和行情侧
就不可能对"这次交易的是哪个所"产生分歧。

## 3. 技术选型

| 领域 | 选择 | 理由 |
|---|---|---|
| 语言 | Rust stable；热路径不用 async | 延迟可预测、无 GC 停顿、无运行时的内存安全 |
| 事件传输 | 环形缓冲（disruptor 模式） | 有界、预分配、无锁交接 |
| Journal | 自研 mmap 追加日志 + 零拷贝序列化 | 现有队列库不能同时满足双时戳、撕裂尾、重放这三项要求 |
| Python 绑定 | PyO3 + maturin，abi3 wheel | 两层共用一套类型系统；wheel 跨 CPython 版本可用 |
| 列式数据 | `arrow-rs` + `parquet-rs` | 与 Python 分析生态零拷贝互通 |
| 数值 | 热路径 `i64` 定点；账本边界用 decimal | 精确的金额运算，浮点永不接触金额 |
| 推理 | ONNX 运行时与编译决策树 | 按模型类别以实测延迟选型，而非按框架偏好 |
| 测试 | `criterion`、`proptest`、自研故障仿真器——**均已采用** | 基准；覆盖 `FR-MATCH-7` 与 `FR-MARGIN-7` 所点名不变量的生成式输入检查——它抓到了一处回绕转换，使得足够大的持仓**完全不需要维持保证金**；以及 `oq-sim` 的场景目录驱动实盘账本——它抓到了重投成交使持仓翻倍。`proptest` 在两个 crate 里都是 dev 依赖，逐 crate 预算不变 |
| 交易所适配器 | 按交易所逐个编写，遵循薄契约 | 通用抽象层恰好隐藏了那些真正引发事故的交易所特有语义 |

## 4.1 仓库布局

架构存在于 **crate 划分**中，而不是目录树里。Cargo 禁止 crate 之间循环依赖，
因此上面那张依赖图是**编译器强制**的，而不是靠约定维持：确定性内核够不到交易所
适配器，因为它根本不依赖包含适配器的那个 crate。这比任何目录安排都强，也正是
"内核里不许有 I/O"在这里是架构性质、而不是一条需要人去记的规矩的原因。

在 crate 内部，模块保持扁平文件，直到某个模块**确实**需要子模块为止。把一个
150 行的模块塞进它自己的目录，只是多了一层路径，不增加任何信息。

```
openquanter/
  Cargo.toml            workspace 清单、共享 lint 与元数据
  crates/
    oq-stats/
      AGENTS.md         本地命令与不变量（就近文件优先）
      Cargo.toml
      src/*.rs          模块还小时保持扁平
    oq-journal/
      src/*.rs          分帧、写入、读取、快照存储
    oq-engine/
      src/
        lib.rs
        book.rs         价格时间优先的订单簿
        l0.rs           tick 回放撮合
        l1.rs、l2.rs     阶梯的其余部分，每一层包住下面一层
    oq-book/
      src/              深度的应用，以及两侧共用的那本簿
    oq-l2feed/
      src/
        *.rs            分帧、密封、深度解析、订单簿重建
        bin/            oq-capture、oq-book-check、oq-merge、oq-resequence
    oq-ingest/
      src/
        agg.rs          从归档到 tick 的按窗口聚合
        bin/            oq-ingest、oq-tiers
    oq-examples/
      examples/         可运行的教学策略
      benches/          criterion 基准
      tests/golden.rs   钉住文档引用的每一个数字
    oq-gateway/
      src/
        exec.rs         每个交易所都要实现的连接器契约
        binance.rs、okx.rs   一家一个适配器
        conformance.rs  两个适配器都要过的那套一致性测试
    ...
  docs/                 需求、路线图、格式规范、快速上手
  scripts/              仓库工具：DCO 检查、秘密扫描、
                        可组合性检查、crate 名称占位
  .github/workflows/    CI：测试、卫生检查、可组合性、吞吐下限
```

有两样东西**刻意不在**这棵树里。没有顶层的 `examples/` 和 `data/`：可运行的示例
本身是一个 crate，因此会随 `cargo test` 一起编译、不会腐烂；而样例
行情是**由种子生成的**而非存下来的，这正是 golden 测试能钉住精确数字、又不必
分发数据集、不必承接任何人的再分发条款的原因。

单元测试与被测代码同文件，放在 `#[cfg(test)]` 模块里——这是 Rust 惯例，也让
不变量紧挨着必须满足它的那个函数。只经公开 API 检验 crate 的集成测试放在
`crates/*/tests/`。

**采集规格**（M0 中不可推迟的部分，因为没采到的那一天永久缺失）：

| 优先级 | 数据流 | 用途 |
|---|---|---|
| 必采 | 增量深度 + 连接时 REST 快照 + 日终快照 | L2 订单簿重建；排队模型输入 |
| 必采 | 最优买卖价（BBO）流 | 真正的逐笔 BBO——深度流是合并降频过的 |
| 必采 | 逐笔成交 | 消耗你前方队列的成交量：排队模型的另一半输入。用**逐笔**而非聚合——是单笔成交，不是按价格与时间预先归并过的成交 |
| 必采 | 标记价 / 资金费率 / 指数价 | 保证金引擎输入；强平按标记价计算。无可用流时改为**轮询**采集——见[采集格式规范](CAPTURE-FORMAT.zh-CN.md) §10 |
| 必采 | 强平订单流 | 稀缺的尾部行为数据，即使被限流也有价值 |
| 应采 | 杠杆与维持保证金分级表（每日快照，双时间） | 保证金规则源；规则会静默变化；存储成本可忽略 |
| 应采 | 持仓量、多空比（周期性 REST） | 成本极低的研究输入 |

格式铁律：每条消息双时戳；原始消息原样归档，聚合是消费侧的事；每次重连打
gap 标记并重拉快照；时钟偏移估计随数据归档。采集运行在带本地存储与压缩批量
归档的专用主机上——这类负载不该放在共享或带宽受限的链路上。

## 6. 测试策略

四层，各自回答一个不同的问题。

| 层 | 回答的问题 | 机制 |
|---|---|---|
| **单元** | 这个函数做的事和它说的一致吗？ | 标准 `cargo test`，快速、按 crate |
| **属性** | 任意输入下不变量还成立吗？ | 数量守恒、价格时间优先、无交叉盘、保证金非负、强平价单调——**均已由 `proptest` 在生成输入上检查**。第一次跑就抓到两件：一处名义价值回绕使大持仓不需要保证金；以及一条**写得太强的性质**——保证金不足以支付自身维持要求的持仓，其强平价确实高于入场价，因为它开仓那一刻就已在线的另一侧。后者是代码对、断言错，被限定条件收窄，而它划出的情况另立为一条性质 |
| **Golden** | 可观察行为变了吗？ | 重放样例数据、比对完整输出；基线携带标识三元组（D13），且只有在记录了人工确认后才可重新生成 |
| **Parity** | 两个实现 / 两种模式一致吗？ | `oq-parity` 逐笔 diff 与归因；用于移植、重构、达速模式、Python/Rust 推理。基线过期一律报为过期，绝不报成差异 |
| **仿真** | 整个系统能在恶劣条件下存活吗？ | `oq-sim` 随机故障注入，每次失败都可由 `(seed, commit)` 复现 |

不可协商的规则：

- 绝不为了让测试通过而削弱不变量。若不变量本身错了，那是一次设计变更，走它自己
  的评审。
- golden 基线更新必须有 PR 中记录的人工确认。agent 或脚本可以**提出**，不能**批准**。
- 比对工具绝不报告它无法归因的差异。若是输入或配置变了，输出就直说（D13），
  而不是把账算到代码头上。
- 公开 CI 完全跑在样例数据上。任何质量门都不得依赖私有数据集。
- 基准在 CI 中对着一条**下限**运行，跌破即构建失败。下限被刻意设在远低于任何真实
  机器的位置：共享 runner 在不同时段能差好几倍，而一个会因噪声误报的门迟早被关掉。
  版本之间的精确比较是在同一台机器上跑 `cargo bench`，不是 CI 的活。

## 7. 性能预算

| 路径 | 预算 | 测量边界 |
|---|---|---|
| 实盘订单发出 | p99 ≤ 100 µs | journal 写入 → 订单字节离开网关 socket |
| 行情解析 | 单列预算并单独报告 | socket 读 → 归一化事件 |
| 请求签名 | 单列预算并单独报告 | 签名入口 → 出口 |
| 内核 `apply()` | 预热后零分配 | 每事件、每分片 |
| GBDT 推理 | 单行 ≤ 10 µs | 特征向量入 → 预测出 |
| 回测吞吐 | ≥ 解释型/Cython 基线的 8× | 墙钟，同机同配置 |
| 参数扫描 | 100 组 ≤ 30 分钟 | 参考机器墙钟 |

延迟一律以直方图报告。均值恰好掩盖了唯一重要的尾部，而交易路径的"平均延迟"这个
数字几乎没有意义。

## 8. 开发流程

- **分支：** 短生命周期分支合入 `main`；`main` 永远绿。
- **提交：** 必须 DCO sign-off（`git commit -s`）；英文提交信息，形如
  `type: short description`。
- **评审：** 每次改动都要说明由哪一层验证覆盖。改动内核的还要说明确定性如何保持。
- **CI：** 构建、测试、`fmt --check`、`clippy -D warnings`、属性测试、golden、
  基准、秘密扫描。
- **代码注释：** 全英文。文档以英文撰写并提供中文对照。
- **每 crate `AGENTS.md`：** 本地命令与不变量，控制在 200 行内，在改动不变量的
  同一个 PR 中更新。

## 9. 开放问题

以下问题记录在案而非就此定论，欢迎以 issue 形式参与讨论。

1. **全仓与组合保证金的范围。** 逐仓与全仓在 M1–M2 范围内。组合保证金各交易所
   差异较大，做通用建模未必划算；藏在 trait 后面的交易所专用实现可能是更好的答案。
2. **参考数据的分发。** 保证金分级表与合约规格体积小、会静默变化、且人人都需要。
   是否分发一份社区维护的双时间数据集、以什么条款分发，是开放问题。
3. **第二、三个交易所的优先级。** 由用户需求驱动；2.0 之前，连接器契约应至少被两个
   结构上不同的交易所验证过。这一条自写下之后已被回答了一部分：OKX 就是第二个，采集
   侧和下单侧都有，而且两侧各有一套两个适配器都能通过的一致性测试。它也验证了"第二个
   交易所"到底是干什么用的——Binance 用 HTTP 状态码回答拒单，OKX 把拒单包在 200 里，
   这类分歧不是靠再多设计就能了结的。仍然敞着的是第三个交易所的优先级，以及 OKX
   的签名那一半——它需要一个真实账户。
4. **排队模型的选择策略。** 校准数据不足时，框架应如何在保守档与概率档之间选择
   ——目前是手动配置，或许应改为自动选择并给出告警。
5. **Python 打包面。** Rust API 暴露多少给 Python 绑定。暴露全部会招致对内部实现
   的耦合；暴露太少又会过早逼用户下沉到 Rust。
