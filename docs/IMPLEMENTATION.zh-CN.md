# OpenQuanter — 实施方案

> 状态：**评审稿** · [English](IMPLEMENTATION.md)
> 配套文档：[需求规格说明](REQUIREMENTS.zh-CN.md) · [路线图](ROADMAP.zh-CN.md)

本文档说明架构、其背后的设计决策、crate 划分，以及交付需求的具体工程计划。
凡是有成熟先例的决策——无论来自开源系统、交易所基础设施还是学术文献——都会点明
先例，使后来的贡献者可以**评估**推理过程，而不是被动继承结论。

## 1. 架构

```
             ┌── 输入适配器 ───────────────────────────────────────────┐
             │  live: 交易所网关 │ backtest: 数据平面 │ sim: 场景生成器 │
             └───────────────────────────┬─────────────────────────────┘
                                         ▼
┌── Sequencer + Journal（oq-journal）─────────────────────────────────────────┐
│  所有事件先编号、先追加写入 mmap journal，再进入内核。journal 同时是：       │
│  审计流、重放源、恢复机制、进程间传输。读端容忍撕裂的尾部记录。             │
└───────────────────────────┬─────────────────────────────────────────────────┘
                            ▼
┌── 确定性内核（oq-core）—— 按标的分片，片内单线程 ───────────────────────────┐
│    fn apply(&mut State, Event) -> Outputs                                   │
│    内部禁止：读时钟 / 随机数 / I/O / 线程。时间是一种事件。                 │
│  ┌─────────────┐ ┌───────────┐ ┌───────────┐ ┌────────────────┐             │
│  │ 撮合        │ │ 保证金    │ │ RiskGate  │ │ 账本           │             │
│  │ oq-engine   │ │ oq-margin │ │ oq-risk   │ │ oq-types       │             │
│  │ L0…L3       │ │ 强平      │ │ 硬上限    │ │ typestate      │             │
│  └─────────────┘ └───────────┘ └───────────┘ └────────────────┘             │
└──────┬──────────────────────┬─────────────────────────┬─────────────────────┘
       ▼                      ▼                         ▼
┌─ 策略层 ───────────┐ ┌─ AI 层 ────────────────┐ ┌─ 输出适配器 ──────────────┐
│ Tier A: Rust trait │ │ oq-infer  （生产级）   │ │ live:     oq-gateway      │
│ Tier B: Python     │ │ oq-env    （RL，受控） │ │ backtest: 成交模拟回注    │
│  兼容 / 达速模式   │ │ oq-lab    （沙盒）     │ │ 观察者读 journal，永不进核│
└────────────────────┘ └────────────────────────┘ └───────────────────────────┘
┌─ 数据平面（oq-data）────────────────────────────────────────────────────────┐
│ Arrow/Parquet 双时戳 │ 双时间参考数据 │ 严格 as-of join                      │
│ oq-l2feed 采集工具   │ oq-features PIT 特征层                               │
└─────────────────────────────────────────────────────────────────────────────┘
```

这个形状导出三条值得明说的性质：

- **回测与实盘只差事件生产者。** 不存在一个需要与实盘引擎保持同步的独立回测引擎。
- **journal 是集成点。** 监控、分析、跨进程聚合都读 journal。除 sequencer 之外，
  没有任何东西能写回内核。
- **确定性不是测试便利，而是恢复机制。** 让 fuzzer 能复现故障的那条性质，也正是
  让崩溃进程能重建状态的那条性质。

## 2. 设计决策

### D1 — 纯确定性状态机内核

内核形如 `apply(State, Event) -> Outputs`，不持有任何环境权限。时间以
`TimeEvent` 进入。这是 LMAX/Aeron 谱系，现代交易框架各自独立收敛到了同一形态。

*推论：* 任何"这里顺手读一下时钟""这里顺手写个日志"都是设计违规，不是风格偏好。
lint 与评审强制它，重放测试兜住漏网的。

### D2 — Sequencer 与 journal 前置于内核

事件在内核观察到之前先编号、先持久追加。这与交易所与行情基础设施中的 tick 捕获
架构、以及同一谱系的内存映射队列库设计一致。

*推论：* 快照由流内事件触发（因此快照落在明确的序列号上）；读端必须容忍最后一条
撕裂记录；"到底发生了什么"永远不取决于日志级别配置。

### D3 — 分片单线程 + 环形缓冲

按标的分片、片内单线程、环形缓冲交接、预分配缓冲、热路径少分支。async 限定在
网关边缘。热路径排除工作窃取调度器，因为其尾延迟不可预测——而这正是 p99 目标
最无法容忍的。

### D4 — 保真度阶梯 + 正交保证金叠加层

执行真实度（L0–L3）与账户真实度（保证金层）是两个独立维度。L0 语义发布后冻结，
充当回归锚点。

`oq-margin` 是独立模块，而不是账户对象上的一个字段：分级维持保证金表按双时间
版本化（交易所会改规则，旧回测必须用旧规则）、逐 tick 占用与强平价、强平单像
普通订单一样进撮合、可注入的资金费尖峰场景。

撮合与保证金都是纯函数，并由属性测试覆盖：数量守恒、价格时间优先、无交叉盘、
保证金占用非负、强平价单调。交易所撮合引擎的形式化方法实践，是把这些当作
机器可检查的不变量（而非评审意见）的先例。

### D5 — 双时戳与固定布局事件

每条行情记录带 `exch_ts` 与 `local_ts`，纳秒精度。事件采用 `repr(C)` 零拷贝
布局。**字段永不复用**——一个字段跨版本改变含义，是电子交易史上代价最惨重的
若干事故背后的共同失效模式。

### D6 — 一核三环境

回测、沙盒、实盘只在适配器与时钟上有差别。这使"我测的策略就是我上的策略"成为
结构性性质，而不是靠纪律维持的习惯。

### D7 — 不可绕过的风控闸门；未知状态即致命

在策略输出与任何交易所之间设置管道级硬检查，外加 kill switch 与启动对账。若
对账无法确立真相，进程拒绝交易。股票市场的盘前风控监管要求编码的是同一原则，
而业内标志性的巨亏事故有着同一个根因：在状态未知时继续动作。

### D8 — 确定性红利：全系统仿真

因为内核是确定性的，随机化故障仿真器可以遍历调度、网络与交易所异常行为，并由
`(seed, commit)` 复现任何一次失败。分布式数据库中的故障注入仿真器是这里的范本。

场景语料以**通用**失败模式作为种子：乱序与重复的成交回报、撤单丢失、合成零价
成交、用户流僵死、重连风暴、时钟跳变、行情 gap。任何运营交易系统的人都会攒出
一份这样的清单；把它编码成可执行场景，就是把运维伤疤变成持久的测试资产。

### D9 — AI 按证据强度分层

- **推理（成熟）。** Python 训练，导出 ONNX 或编译梯度提升树，在 Rust 进程内
  运行，intra/inter-op 单线程、预热、固定形状。设 parity 门比对 Python 与 Rust
  的预测，因为树模型的 float32 阈值处理在不同实现间会漂移，而这种漂移会静默地
  改变交易决策。
- **训练（受控）。** 控制反转的 gym 式环境 + 原生向量化批处理。以 L1 保真度为
  前置：在低保真环境训练会产出利用仿真器缺陷的策略。
- **探索（时间盒）。** LLM 沙盒，配类型化只读工具 API 与审计日志。仅用模型训练
  截止日之后的数据评估。模型输出是提案；硬限制留在引擎层。

### D10 — 数据层的 PIT 正确性

任何会追溯变更的数据（资金费时刻表、保证金分级、合约规格、上下架）双时间存储。
as-of join 默认严格 `<`，因为常见 dataframe 库的闭区间语义会把同时戳信息泄漏进
特征。一份特征代码同时服务研究与实盘，并用线上/线下一致性度量来证明它。

### D11 — 为 coding agent 设计的代码库

每个 crate 一份 200 行以内的 `AGENTS.md`，写明本地命令与不变量。分层验证锚
——单测 → 属性 → golden → parity——使 agent 或新贡献者无需把整个系统装进脑子
就能判断一次改动是否安全。golden 基线变更需要 PR 中的人工显式确认。

这同时也是 bus-factor 的缓解手段：这个领域的项目往往死于唯一维护者离开，而防线
是**写下来、可机器校验的行为**，而不是描述意图的文档。

### D12 — 运行拓扑与安全

- **每账户一进程。** 一个进程拥有一个账户、其策略与自己的 journal。故障域不重叠，
  一个账户的对账失败不会污染另一个。组合层视图由读 journal 构建，而不是共享
  交易状态。
- **凭证处理。** API key 永不出现在提交的配置中；从环境变量或 OS keyring 注入，
  且只存在于网关进程内存中；研究与回测进程没有访问路径。
- **时钟纪律。** 主机运行 NTP/chrony。采集进程在启动时记录时钟偏移估计并随数据
  归档——建立在未经校验的本机时钟之上的延迟建模，地基是歪的。

### D13 — 基线由内容标识，而不是由 commit 标识

只钉在代码 commit 上的回归基线会**静默失效**。输入数据被修正、某个配置默认值挪
了、数据集重新导出了——代码没动，于是基线看上去仍然有效，而下一次比对报出的
mismatch 根本不是回归。

这种失效模式比"漏掉一次回归"更糟：它给出的是一个**自信的错误答案**，读到它的人
无法区分"引擎变了"和"输入变了"，接下来的时间会花在二分一段根本没问题的代码上。

因此本项目中每一条 parity 与 golden 基线都由三元组标识：**(代码 commit、输入
数据内容哈希、生效配置哈希)**，比对工具必须对自己的输出做分类：

| 三元组状态 | 报告 |
|---|---|
| 三元全部一致 | 差异是**行为性**的——一次需要排查的回归 |
| 任一元不一致 | **`基线已失效——需 rebase`**，并指明是哪一元变了 |

对输入做哈希只花微秒级开销，却消除了一整类误诊。该规则同样适用于 golden 测试：
样例数据变了的 golden 基线是**过期**，不是**被违反**。

## 3. 技术选型

| 领域 | 选择 | 理由 |
|---|---|---|
| 语言 | Rust stable；热路径不用 async | 延迟可预测、无 GC 停顿、无运行时的内存安全 |
| 事件传输 | 环形缓冲（disruptor 模式） | 有界、预分配、无锁交接 |
| Journal | 自研 mmap 追加日志 + 零拷贝序列化 | 现有队列库不能同时满足双时戳、撕裂尾、重放这三项要求 |
| Python 绑定 | PyO3 + maturin，abi3 wheel | 两层共用一套类型系统；wheel 跨 CPython 版本可用 |
| 列式数据 | `arrow-rs` + `parquet-rs` | 与 Python 分析生态零拷贝互通 |
| 数值 | 热路径 `i64` 定点；账本边界用 decimal | 精确的金额运算，浮点永不接触金额 |
| 推理 | ONNX 运行时与编译决策树 | 按模型类别以实测延迟选型，而非按框架偏好 |
| 测试 | `proptest`、`criterion`、自研故障仿真器 | 分别负责不变量、基准、全系统 fuzz |
| 交易所适配器 | 按交易所逐个编写，遵循薄契约 | 通用抽象层恰好隐藏了那些真正引发事故的交易所特有语义 |

## 4.1 仓库布局

架构存在于 **crate 划分**中，而不是目录树里。Cargo 禁止 crate 之间循环依赖，
因此上面那张依赖图是**编译器强制**的，而不是靠约定维持：确定性内核够不到交易所
适配器，因为它根本不依赖包含适配器的那个 crate。这比任何目录安排都强，也正是
"内核里不许有 I/O"在这里是架构性质、而不是一条需要人去记的规矩的原因。

在 crate 内部，模块保持扁平文件，直到某个模块**确实**需要子模块为止。把一个
150 行的模块塞进它自己的目录，只是多了一层路径，不增加任何信息。

```
openquanter/
  Cargo.toml            workspace 清单、共享 lint 与元数据
  crates/
    oq-stats/
      AGENTS.md         本地命令与不变量（就近文件优先）
      Cargo.toml
      src/*.rs          模块还小时保持扁平
    oq-journal/
      src/*.rs          分帧、写入、读取、快照存储
    oq-engine/
      src/
        lib.rs
        book.rs         价格时间优先的订单簿
        l0.rs           tick 回放撮合；l1.rs、l2.rs 随后
        matching/       阶梯长大后再拆子模块
    oq-gateway/
      src/
        contract.rs     每个交易所都要实现的连接器契约
        binance/        market_data.rs、orders.rs、user_stream.rs、reconcile.rs
    ...
  docs/                 需求、路线图、实施方案
  scripts/              仓库工具（DCO 检查、名称占位）
  examples/             示例策略
  data/                 样例数据集与 golden 基线
  crates/*/tests/       集成测试，与模块内单测分开
  crates/*/benches/     criterion 基准，在 CI 中被跟踪
```

单元测试与被测代码同文件，放在 `#[cfg(test)]` 模块里——这是 Rust 惯例，也让
不变量紧挨着必须满足它的那个函数。只经公开 API 检验 crate 的集成测试放在
`tests/`。

## 5. 执行计划

任务 ID 用作 issue 与 PR 的稳定引用。

### Phase 0 — 地基（M0）

| ID | 任务 | 完成标准 |
|---|---|---|
| P0.1 | 仓库规范：DCO 检查 Action、CLA 文本、crates.io 名称占位、Rust edition 升级 | CI 强制 sign-off；`oq-*` 名称已占位 |
| P0.2 | `oq-stats`：DSR、PBO/CSCV、试验计数 | 统计可在真实扫描输出上计算，并对照公开算例做单测 |
| P0.3 | `oq-l2feed` 设计与试采 | 7 天试采：实测流量、gap 率、存储成本，时钟偏移归档验证通过 |
| P0.4 | `oq-l2feed` 常驻运行 | 采集以服务形式运行并有监控；每日保证金分级表快照持续累积 |
| P0.5 | 场景目录 | ≥ 6 条通用失败场景，写成可复现描述 |
| P0.6 | 延迟与成交结果采样方法 | 有文档化的离线流程，从运行日志中提取延迟与成交样本 |

**采集规格**（M0 中不可推迟的部分，因为没采到的那一天永久缺失）：

| 优先级 | 数据流 | 用途 |
|---|---|---|
| 必采 | 增量深度 + 连接时 REST 快照 + 日终快照 | L2 订单簿重建；排队模型输入 |
| 必采 | 最优买卖价（BBO）流 | 真正的逐笔 BBO——深度流是合并降频过的 |
| 必采 | 逐笔成交 | 消耗你前方队列的成交量：排队模型的另一半输入。用**逐笔**而非聚合——是单笔成交，不是按价格与时间预先归并过的成交 |
| 必采 | 标记价 / 资金费率 / 指数价 | 保证金引擎输入；强平按标记价计算。无可用流时改为**轮询**采集——见[采集格式规范](CAPTURE-FORMAT.zh-CN.md) §10 |
| 必采 | 强平订单流 | 稀缺的尾部行为数据，即使被限流也有价值 |
| 应采 | 杠杆与维持保证金分级表（每日快照，双时间） | 保证金规则源；规则会静默变化；存储成本可忽略 |
| 应采 | 持仓量、多空比（周期性 REST） | 成本极低的研究输入 |

格式铁律：每条消息双时戳；原始消息原样归档，聚合是消费侧的事；每次重连打
gap 标记并重拉快照；时钟偏移估计随数据归档。采集运行在带本地存储与压缩批量
归档的专用主机上——这类负载不该放在共享或带宽受限的链路上。

## 6. 测试策略

四层，各自回答一个不同的问题。

| 层 | 回答的问题 | 机制 |
|---|---|---|
| **单元** | 这个函数做的事和它说的一致吗？ | 标准 `cargo test`，快速、按 crate |
| **属性** | 任意输入下不变量还成立吗？ | `proptest`：数量守恒、价格时间优先、无交叉盘、保证金非负、强平价单调 |
| **Golden** | 可观察行为变了吗？ | 重放样例数据、比对完整输出；基线携带标识三元组（D13），且只有在记录了人工确认后才可重新生成 |
| **Parity** | 两个实现 / 两种模式一致吗？ | `oq-parity` 逐笔 diff 与归因；用于移植、重构、达速模式、Python/Rust 推理。基线过期一律报为过期，绝不报成差异 |
| **仿真** | 整个系统能在恶劣条件下存活吗？ | `oq-sim` 随机故障注入，每次失败都可由 `(seed, commit)` 复现 |

不可协商的规则：

- 绝不为了让测试通过而削弱不变量。若不变量本身错了，那是一次设计变更，走它自己
  的评审。
- golden 基线更新必须有 PR 中记录的人工确认。agent 或脚本可以**提出**，不能**批准**。
- 比对工具绝不报告它无法归因的差异。若是输入或配置变了，输出就直说（D13），
  而不是把账算到代码头上。
- 公开 CI 完全跑在样例数据上。任何质量门都不得依赖私有数据集。
- 基准在 CI 中运行并跟踪基线；性能回退是构建失败，不是一条备注。

## 7. 性能预算

| 路径 | 预算 | 测量边界 |
|---|---|---|
| 实盘订单发出 | p99 ≤ 100 µs | journal 写入 → 订单字节离开网关 socket |
| 行情解析 | 单列预算并单独报告 | socket 读 → 归一化事件 |
| 请求签名 | 单列预算并单独报告 | 签名入口 → 出口 |
| 内核 `apply()` | 预热后零分配 | 每事件、每分片 |
| GBDT 推理 | 单行 ≤ 10 µs | 特征向量入 → 预测出 |
| 回测吞吐 | ≥ 解释型/Cython 基线的 8× | 墙钟，同机同配置 |
| 参数扫描 | 100 组 ≤ 30 分钟 | 参考机器墙钟 |

延迟一律以直方图报告。均值恰好掩盖了唯一重要的尾部，而交易路径的"平均延迟"这个
数字几乎没有意义。

## 8. 开发流程

- **分支：** 短生命周期分支合入 `main`；`main` 永远绿。
- **提交：** 必须 DCO sign-off（`git commit -s`）；英文提交信息，形如
  `type: short description`。
- **评审：** 每次改动都要说明由哪一层验证覆盖。改动内核的还要说明确定性如何保持。
- **CI：** 构建、测试、`fmt --check`、`clippy -D warnings`、属性测试、golden、
  基准、秘密扫描。
- **代码注释：** 全英文。文档以英文撰写并提供中文对照。
- **每 crate `AGENTS.md`：** 本地命令与不变量，控制在 200 行内，在改动不变量的
  同一个 PR 中更新。

## 9. 开放问题

以下问题记录在案而非就此定论，欢迎以 issue 形式参与讨论。

1. **全仓与组合保证金的范围。** 逐仓与全仓在 M1–M2 范围内。组合保证金各交易所
   差异较大，做通用建模未必划算；藏在 trait 后面的交易所专用实现可能是更好的答案。
2. **参考数据的分发。** 保证金分级表与合约规格体积小、会静默变化、且人人都需要。
   是否分发一份社区维护的双时间数据集、以什么条款分发，是开放问题。
3. **第二、三个交易所的优先级。** 由用户需求驱动；1.0 之前连接器契约应至少被两个
   结构上不同的交易所验证过。
4. **排队模型的选择策略。** 校准数据不足时，框架应如何在保守档与概率档之间选择
   ——目前是手动配置，或许应改为自动选择并给出告警。
5. **Python 打包面。** Rust API 暴露多少给 Python 绑定。暴露全部会招致对内部实现
   的耦合；暴露太少又会过早逼用户下沉到 Rust。
