# 更多交易所

[English](VENUES.md) · [中文](VENUES.zh-CN.md)

要把 Coinbase、Backpack、Kraken、Bitget、Lighter、Hyperliquid、Aster 接进一个
目前只会说两家交易所的网关,需要付出什么;以及在写下其中任何一个的第一行代码
之前,必须先改掉什么。

先做设计,理由和[实盘路径](LIVE-PATH.zh-CN.md)当初一样:那份调研看了九个系统,
每一个都先建下单路径、把对账留到后面,而每一个都带着同一类 bug。这件事上对应的
错误,是照着头两家交易所碰巧需要的形状去写七个适配器。

## 这份文档的立论

**七家交易所不是七个问题。** 它们是四个签名家族、三处结构性差异,外加一个关于
密码学的问题——那个问题不回答,三家去中心化交易所一家都开不了工。按这个方式
分类之后,七家里有两家几乎是白送的,还有一家大概根本不该做。

## 调研发现了什么

### Coinbase 的永续已经不在 Coinbase 了

Coinbase International Exchange 于 **2026-09-09** 停止提供衍生品服务,就在写下
这份文档的九天前。Coinbase App 和 coinbase.com 上的永续现在跑在 Deribit 驱动的
网关上,API 用户被迁到了一个 **JSON-RPC** 端点。这份文档本来要瞄准的那套 INTX
REST API,在 Coinbase 自己的开发者文档里已经标为废弃。

所以写一个 INTX 适配器,等于给一个已经关掉的东西写适配器。真正的目标是 Deribit
的 JSON-RPC——那不是这里这些 REST 交易所的一个变体,而是另一个协议族,有它自己
的请求/响应标识模型。

这是这次调研最好的成果:它减少了工作量,而不是增加。

### Bitget 也在搬,而且三天前刚开始

Bitget 从 **2026-09-15** 起按用户活跃度分批把 classic 账户迁移到**统一交易账户
(UTA)**。对 API 的后果在它自己的升级指南里写得很直白:**UTA 的 key 调不了 classic
端点**。用 classic API (v2) 的集成必须迁到 UTA API (v3)。

也就是说,这份文档本来要瞄准的那些 `/api/v2/mix/*` 路径,正是每一个被迁移的账户
上会停止工作的路径,而迁移是正在进行时,不是"已宣布"。写一个 classic API 的适配器,
就是把 Coinbase 那个错误再犯一遍,只不过这次的提前量是三天而不是九天。

目标是 UTA v3。那不是改个名字:它是另一套账户模型——跨产品的一个余额,而不是每个
合约一种保证金币种——所以即便签名不变,持仓和余额的读取形状也是不同的。

**七家里有两家正处在迁移中。** 这是这次调研为"先调研"给出的最有力论据:两家都是
在动手写适配器之前、靠读交易所自己的文档发现的,否则就会靠"适配器突然不工作了"
来发现。

### 四个家族

| 家族 | 成员 | 形状 |
|---|---|---|
| **Binance** | `binance`(已建)、**Aster** | 对 query string 做 `HMAC-SHA256` 取 hex;`timestamp` + `recvWindow` |
| **OKX** | `okx`(已建)、**Bitget** | `HMAC-SHA256(timestamp + METHOD + path + body)` 取 base64;key/secret/**passphrase** 三元组 |
| **Kraken** | **Kraken Futures** | `SHA-256(postData + nonce + path)`,再用 base64 解码后的 secret 做 `HMAC-SHA-512`,再 base64。请求头是 `APIKey` 和 `Authent` |
| **非对称** | **Backpack**(Ed25519)、**Hyperliquid**(secp256k1 / EIP-712)、**Lighter**(自有方案,每个 key 独立 nonce) | 是密钥对,不是共享密钥 |

Aster 的文档写的是对"query string 拼接 request body"做 `HMAC SHA256`,带
`timestamp`,`recvWindow` 默认 5000——这就是 Binance 的方案换了个说法。Bitget 签的是
`timestamp + METHOD + requestPath + "?" + queryString + body` 再 base64,请求头是
`ACCESS-KEY` / `ACCESS-SIGN` / `ACCESS-PASSPHRASE`——这就是 OKX 的方案换了组头名。

**所以七家里有两家落进了已经存在的家族。** 它们是这张清单上最便宜的活,也是
最有信息量的:它们能说明现有抽象到底是不是通用的,而这件事值得在昂贵的那几家
开工之前就知道。

### 三处结构性差异

有三件事把交易所区分开来,而签名家族这个维度看不见它们。

**1. 用什么标识一个合约。** 目前建成的两家都接受符号字符串。Hyperliquid 接受的是
**数字资产索引**——它在 `meta` 响应的 `universe` 数组里的位置,现货资产则是
`10000 + index`。现在的 `Instrument` 和任何一个调用签名里都没有这个东西。适配器
必须在加载时把符号解析成索引并保存这个映射,而这个映射在交易所元数据更新后不保证
稳定。

**2. 一帧里有几个事件。** Binance 的用户流一条消息一个事件。OKX 的 `orders` 频道
发的是 `data` **数组**,Hyperliquid 的下单响应返回 `statuses` 数组——批量里一个
订单一条。一个只返回第一条、丢掉其余的读取器会丢掉一笔成交,而丢掉的成交就是一个
从未存在过的仓位。

**3. 客户端订单号会不会比订单活得久。** 实盘路径设计里的 `L4` 要求客户端订单号
可重建,已建成的两家都守着它:一个客户端 id 对一个交易所 id,终其订单一生。
**而 Hyperliquid 的改单是撤单重下**——它撤掉原单(旧 `oid`),开一个替代单
(新 `oid`),两者带着**同一个 `cloid`**。于是这个映射在时间上是一对多的,一张
以客户端 id 为键的去重表会看到两个订单,而策略只看到一个。NautilusTrader 的适配器
的做法是压掉那条过期的撤单、把替代单的接受提升成一个 `OrderUpdated`;不管这个
工作区最后怎么做,它都必须做点什么,因为默认行为是账本认为一个还挂着的订单被撤了。

### 别人为此付过什么代价

NautilusTrader 有一个用 Rust 写的 Hyperliquid 适配器,它的集成文档是这次调研
找到的最有用的东西——那是一份清单,列着这家交易所会做哪些一个讲道理的实现者
预料不到的事:

- **价格精度超标会报成 `user or API wallet does not exist`。** 价格被限制在五位
  有效数字,超了会让签名验证失败,而交易所把这件事报告成钱包不存在。这和 Binance
  在这里第一次真跑时发现的那个缺陷是同一类——价格小数位数对但不在 tick 网格上
  ——只不过这条错误消息指向了一个完全不相干的地方。
- **agent wallet 下的单属于主账户**,而一个没有显式设置主账户地址的客户端,从 REST
  拿到的是空持仓、用户流是空的、订单永远对不上。什么都连上了,什么都对不上。
- **没有市价单。** 它是用一个按滑点调整过价格的 IOC 限价单模拟的,而这需要一份
  缓存的报价——于是下单路径依赖行情路径,这在今天这里的任何一家交易所上都不成立。
- **限流有一部分是挣来的。** 10000 个 action,外加每累计成交 1 USDC 多给一个,撤单
  另有额度。一个随成交量增长的额度,不是 `oq-live` 的限流器假设的那种固定的
  每分钟权重模型。

CCXT 关于签名开销的记录也值得写下来:纯语言实现的 ECDSA 签一次大约 45 毫秒,而
原生曲线库不到 0.05 毫秒。**45 毫秒的签名是坐在下单路径上的**,而这个工作区有一道
延迟门槛(`G6`),量的是从 journal 落盘到 socket 写出。下面那个密码学问题不管怎么
回答,答案上都挂着一个数字。

## 密码学这个问题

`scripts/check-composability.sh` 把政策写下来了,而且写得很明确:

> 签名和 JSON 解析是手写的而不是引入的:这是持有 API secret 的 crate,这里每多一个
> 依赖,就多一样东西被信任持有它。

这条政策对 SHA-256 和 HMAC 是负担得起的——它们是确定性的位运算,有公开的测试
向量,`oq-hash` 过了 RFC 4231。对非对称方案就负担不起了:

- **Kraken** 需要 **SHA-512**,`oq-hash` 没有。这一个*是*负担得起的:它和 SHA-256
  是同一种活,有同一类向量可以对。
- **Backpack** 需要 **Ed25519**。**Hyperliquid** 需要 **secp256k1 ECDSA 加
  Keccak-256** 来做 EIP-712。**Lighter** 需要它自己的方案,在某条曲线上,还带着
  每个 API key 独立的 nonce。

手写椭圆曲线运算和手写一个哈希不是同一件事。它是常数时间的域运算、点乘,而对
ECDSA 来说还有 nonce 生成——那里一个偏差就泄露私钥。这些密钥不只是用来下单的:
一把钱包私钥能把钱转走。**安全的选项只有两个:要么引入一个经过审计的依赖,要么
不做这几家交易所**,假装还有第三个选项,就是一个工作区最后拥有自己那套曲线实现的
由来。

预算表里说,提高预算是一个刻意的动作,要在加入依赖的那个提交里做出,并说明它买到了
什么。真到那一步时,这就是那个动作:每条曲线一个条目,写明名字,并把被否决的那个
替代方案记下来——是"否决过",不是"没想过"。

## 决策

### V1 —— 按签名家族组织,而不是按中心化/去中心化

直觉上的切法是中心化对去中心化。这个轴是错的:**Aster 是一家永续 DEX,而它的 API
就是 Binance 的**,连 `recvWindow` 默认 5000 都一样;而 Backpack 是一家中心化
交易所,却需要 Ed25519。按"请求怎么签名、订单用什么标识"来分,能把可复用的工作
放在一起,把真正新的工作放到它该在的地方。

### V2 —— 两个家族成员先做

Aster 和 Bitget 最便宜,也最有信息量。它们各自落进一个已经存在的家族,所以每一个
都是对"抽象到底通不通用"的检验——还是说那些抽象只是编码了某一家交易所的习惯。
如果加 Aster 需要去改 `binance.rs`,那说明抽象是错的,而从一家花几天的交易所身上
学到这件事,比从一家花几周的身上学到要好得多。

### V3 —— Coinbase 要么意味着 Deribit,要么什么都不意味

INTX 适配器瞄准的是一个已经关掉的服务。要么把目标改成 Deribit 的 JSON-RPC 网关
——一个这里还没有任何成员的协议族,工作量比这张清单上任何一家 REST 交易所都大
——要么 Coinbase 从清单上撤下来。记录在案,而不是悄悄划掉。

### V4 —— 交易所读取器返回列表,不是 Option

`Events::read` 目前答的是 `Option<UserEvent>`。OKX 的 `orders` 频道和 Hyperliquid
的 `statuses` 都会带好几个。签名改成列表,`UserStreamReader` 把多出来的放进一个
队列,`next` 先把队列排空再去读 socket。这不是为 Hyperliquid 做的改动——正在做的
OKX 那部分工作已经要求它了。

### V5 —— 解析合约是适配器的职责,而且它有状态

Hyperliquid 的数字资产索引总得从某个地方来,而那个地方是适配器自己取回并保存的
`meta` 响应。`Instrument` 类型保持干净:变的是适配器在能交易一个符号之前,可能
需要先被*准备*好——这件事今天只在"读一次 listing"这个很弱的意义上成立。把准备
这一步显式化,也顺便给 Hyperliquid 那个五位有效数字的价格上限找到了安放之处,于是
一个精度超标的价格在这里就被拒绝,而不是换回来一句钱包不存在。

### V6 —— 一个客户端订单号可能比它的交易所订单号活得久

`L4` 依然成立,但它隐含的那条不变量——一个客户端 id 对一个交易所 id——是 Binance
和 OKX 的性质,不是交易所的性质。订单账本模型需要能接受"交易所 id 在一个稳定的
客户端 id 之下发生变化",以及一个不会把替代单当成第二个订单的去重键。不管这件事
最后长成什么样,它在这里决定一次,而不是在每个适配器里各自重新发现一遍。

### V7 —— 文档形状要被标成文档形状

每个适配器的 conformance 载荷都会来自交易所的公开文档,因为没有账号可以用来抓
真实的。`okx.rs` 已经带着正确的声明,它就是范本:

> 它没有对 OKX 真跑过。这里每个纯函数都是对着交易所文档里的形状测的,而那和真的
> 下过一单不是一回事。[…] 假定这一个也有它自己的五个。

每个新适配器都带上同一段话,写明自己那家交易所的名字,并且在有人真跑过之前不进
`Endpoint::Live`。一个没法诚实地说出这段话的模块,还不到可以合并的时候。

### V8 —— 拒绝默认从 body 里读,所有交易所都是

Binance 用 HTTP 状态码说不。OKX 用 HTTP 200 加一个 code 说不。**Hyperliquid 也是
用 HTTP 200 说不**,藏在 `statuses[].error` 里。四个家族里已经有两个把拒绝放在
body 里,所以 body 是规则、状态行才是例外——`classify` 是对的,每个新适配器在做
任何别的事情之前先实现它,并为这件事本身写一条 conformance 用例。

## 逐个交易所的备注,附把握程度

| 交易所 | 家族 | 把握 | 最可能咬人的地方 |
|---|---|---|---|
| **Aster** | Binance | 高——文档已读 | 它的永续语义是否和签名一样贴近 Binance |
| **Bitget** | OKX(仅签名) | 中——签名已读,但目标搬家了 | 正在迁往 UTA v3;而且所谓同族只同在签名——成功码是 `"00000"` 而不是 `"0"`,数量单位是**币量**,而 OKX 数的是张数 |
| **Kraken Futures** | Kraken | 中——算法已确认,订单语义未确认 | 需要 SHA-512;符号是 `PF_XBTUSD`,所以符号映射不是装饰性的 |
| **Backpack** | Ed25519 | 中——签名方案已读 | 参数在签名前要按字母序排序,这本身就是一整类 bug |
| **Hyperliquid** | secp256k1 | 中高——交易所文档和一个 Rust 适配器的笔记都读了 | 见"别人为此付过什么代价"整节 |
| **Lighter** | 自有方案 | **低** | 每个 API key 独立的 nonce、key 索引 0–254 且 0–3 被保留、以及一套这次调研还没好好读过的签名方案 |
| **Coinbase** | —— | 不适用 | 它搬走了。见 V3 |

Lighter 的把握是刻意写成"低"的。凭记忆写它会产出一个能编译、能通过自己的测试、
而且错得没人看得见的东西——那比没有它更糟。

## 顺序

1. **把 OKX 收尾** —— 账户侧的读取已落地,握手已落地;还剩读取器和 `Account`。
   它是模板,而一个带着窟窿的模板会把窟窿一起教下去。
2. **Aster** —— 家族检验,而且通过了:整个交易所就是一张路径表,因为它的 API
   *就是* Binance 的。
9. **Bitget 走 UTA v3**,等它的形状被读清楚之后。从"便宜"降级:所谓共享的家族
   原来只是签名——成功码不同、数量是币量不是张数、而且账户模型正在被替换。
3. **`oq-hash` 增加 SHA-512**,然后 **Kraken Futures** —— 一个新家族,外加那唯一
   一件诚实地手写得了的密码学。
4. **依赖决策**,显式地做,改掉预算表,把理由记下来。
5. **Backpack** —— 最简单的非对称方案,因此也是最适合用来证明第 4 步那个决策
   管用的那一个。
6. **Hyperliquid** —— 要求最高,也是唯一有 Rust 实现可以对照着读的。
7. **Lighter** —— 等它自己的一次调研之后。
8. **Deribit**,或者 Coinbase 从清单上撤下来。

每一步是一个 pull request,而第 2 到第 7 步每一步都以写下 conformance 载荷开始,
以适配器通过它们结束。

## 这份文档不覆盖什么

行情。这里每一家交易所同时也发布盘口和成交流,而 `oq-l2feed` 有它自己的交易所
抽象和它自己的 conformance 套件。两侧是刻意分开的——同一家交易所的执行适配器和
采集适配器是两个不同的对象——把七家交易所加到采集侧,是另一份文档的事。
