# 版本规则

> [English](VERSIONING.md)

**"这是什么版本"只有一个答案。** 这份文档存在，是因为曾经有三个。

## 规则

工作区里每个 crate 的版本相同，在根 `Cargo.toml` 里声明一次，各 crate 用
`version.workspace = true` 继承。内部依赖也在 `[workspace.dependencies]` 里声明
一次——所以升版本是**一处修改**，不可能在 crate 之间漂移。

```
2.0.0, 2.0.1, 2.0.2, …   一个接一个的发布，每个对应一个 tag vX.Y.Z
```

一次发布就是序列里的一个数字、`main` 上的一个 tag。下一次就是上一次的第三位加一。
这个数字只说明**是哪一次发布**，别的什么都不表示：没有 alpha，没有 beta，数字里
也不编码任何承诺。

这些 crate 是**同一列发布火车**。它们是可分离的——单独使用其中一个是被支持且被
测试的性质（G0）——但它们一起开发、一起测试、一起发布，读者对比两个检出时不该
需要去调和二十三个数字。

## 为什么是 2，而公开的东西从来没有过 1

OpenQuanter 1.x 是一个闭源交易平台，实盘运行了数年。它从未公开，也不会公开。
本项目是它的继任者，从零重写——**叫 2 只是对这件事的如实陈述**。

由此产生的结果是公开记录里有一个缺口：crates.io 和这个仓库都从 2.0
开始，**不存在可供查找的公开 1.x**。这一点写在这里、而不是留作谜题，因为一个
缺失的主版本号在读者眼里默认是个错误。

## 一次发布承诺什么

承诺它能构建、通过完整门禁、并且有说明。每次发布都从一个全绿的 `main` 切出；它的
说明就是[变更日志](../CHANGELOG.zh-CN.md)里对应的那一节；任何对 L0 撮合语义、保证金
计算或事件格式的改动都会在那里显式写出。

它**不**承诺 API 稳定。在到达[路线图](ROADMAP.zh-CN.md)的 API 稳定里程碑之前，任何
公开 API 都可能在相邻两次发布之间改变，没有弃用缓冲期。那项承诺是一个由文档宣布的
里程碑，而不是从版本号里读出来的东西——读者不必去解码数字才能知道它。

本页早先的版本用 `2.0.0-alpha.N` 来表达这个信号。2026-10-01 改成了简单的递增序列：
一套真正在用的发版规则，胜过一套更丰富却从没真正发过版的规则。唯一发布过的预发布
版本是 PyPI 上的 `2.0.0a1`（2026-08-18），它排在 `2.0.0` 之前，保持原样。

## 刻意独立编号的东西

不是所有东西都跟随 crate 版本，因为它们并不随之变化：

| 制品 | 版本位置 | 规范 |
|---|---|---|
| 采集文件格式 | manifest 里的 `format_version`，当前为 2（读者仍接受 1） | [采集格式规范](CAPTURE-FORMAT.zh-CN.md) |
| Tick 文件格式 | 文件头里的 `version`，当前为 2 | [Tick 格式规范](TICK-FORMAT.zh-CN.md) |
| Journal 帧格式 | 帧头里的 `VERSION` | `oq-journal` |
| run 文件格式 | 第一行的 `openquanter-run N`，当前为 1 | [run 文件格式](RUN-FORMAT.zh-CN.md) |
| 扫描文件格式 | 第一行的 `openquanter-sweep N`，当前为 1 | [扫描文件格式](SWEEP-FORMAT.zh-CN.md) |

**数据格式比写它的代码活得久。** 把格式版本绑到 crate 版本上，要么每次发布都要升
格式版本——那这个数字就没有意义了；要么让它落在后面——那它就是个谎。它们是两个
数字，因为回答的是两个问题：crate 版本说的是**你在对着什么 API 编译**，格式版本
说的是**磁盘上那个文件里装着什么**。

## 发布到哪里

| 产物 | 仓库 | 状态 |
|---|---|---|
| 发布说明、Linux 二进制 | [GitHub Releases](https://github.com/openquanter/openquanter/releases) | 每个 tag 一个，从 `2.0.0` 起 |
| `openquanter`（Python） | [PyPI](https://pypi.org/project/openquanter/) | 从 `2.0.0` 起由发布流水线发布；`2.0.0a1` 是手动上传的 |
| `oq-*`（Rust） | crates.io | 名称已占位，未发布任何版本 |

Python 包先行、Rust crate 后发，是有意为之。一个绑定的暴露面是小的、被刻意挑
选过的——统计量和策略层——它的用户是在评估这东西值不值得花时间的人。而一个 crate
会暴露工作区里每一个 public 类型，而这些类型还在动。现在发布等于把人钉在一个即将
在他们脚下改变的版本上，而一个从 crates.io 撤下的版本，仍然是有人据以构建过的版本。

**这些 crate 什么时候上架。** 不是按日期。条件就是本节已经给出的那个：工作区的
类型不再移动。这就是路线图里的 API 稳定里程碑——它把 API 稳定化放在 M3 之后、
外部采用之后——所以 crate 在"它暴露的 API 已经是别人可以据以构建、而不会被挪走"的时候
发布。在那之前，安装路径就是 `git clone`，[快速上手](QUICKSTART.zh-CN.md)如实
这么写，而不是给出一条会成功、却交付一个空 crate 的 `cargo install`。

这个矛盾真实存在过。本页写着**未发布任何版本**，而快速上手把五条 `cargo install`
列为第一件要做的事；照做的读者拿到的是占位包，而且不报错。两份文档，对同一个事实
给出相反的说法。

顺带说明：PyPI 的版本同样不可重传。每个版本都是永久的，所以随它一起发出去的元
数据——描述、README、分类标签——是在上传**之前**检查的，而不是事后再改；发布流水线
也因此先构建并测试 wheel，然后才发布任何东西。

## 怎么改版本

改根 `Cargo.toml` 里的 `[workspace.package].version` 和 `[workspace.dependencies]`
中的版本。**没有别的地方。** 如果你发现自己在改 `crates/*/Cargo.toml` 里的版本，
说明有东西漂回去了，应该把它重新指向 workspace。

## 怎么发版

1. 在一个 PR 里：按上一节改版本号，并把变更日志（中英两版）的 `Unreleased` 标题
   改成 `X.Y.Z — <日期>`，在它上面新开一个空的 `Unreleased`。
2. 合并后，在 `main` 的那个提交上打 tag 并推送：
   `git tag -a vX.Y.Z -m vX.Y.Z && git push origin vX.Y.Z`。
3. 剩下的由 `.github/workflows/release.yml` 完成，任何一步对不上都会拒绝：tag 必须
   等于工作区版本，提交必须在 `main` 上，完整门禁必须通过，变更日志必须有该版本的
   一节。然后它构建 Linux 二进制和 wheel，创建 GitHub Release（说明取自那一节，附上
   二进制和校验和），并通过 trusted publishing 把 wheel 发到 PyPI——任何地方都不保存
   token。

流水线失败的 tag 什么都不会发布。在 `main` 上修好，发下一个号；版本号一旦打过 tag，
就不再复用。
