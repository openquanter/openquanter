# 执行

> [English](EXECUTION.md)
> 配套文档:[实盘路径](LIVE-PATH.zh-CN.md) · [路线图](ROADMAP.zh-CN.md)

一张单如何送到交易所、它的结局如何回来,以及当这两者对不上时框架怎么办。

## 交易所强加的形状

交易所用两种传输说话,而它们**不是二选一**。

| | 方向 | 承载 | 认证 |
|---|---|---|---|
| **HTTPS/JSON** | 客户端主动问 | 下单、撤单、查询、账户 | 每个请求单独签名 |
| **WebSocket** | 交易所推送 | 订单状态、成交、账户变动 | 一次,用 HTTPS 取到的 key |

任何一半都不够。只有 HTTPS,想知道成交只能再问一遍——把推送变成轮询,既丢事件顺序
也丢掉了策略赖以成立的延迟;只有 WebSocket,什么都发不出去。

所以**一个执行适配器是两个必须互相印证的半边,跑在两条会独立断开的连接上。这是本设计
的中心事实。** 把交易所建模成单一通道的网关,总有一天会因为"本该告诉它的那条 socket
断了"而认定一张单从未下出去。

## 一张单到底是什么

一张单不是"发出去会返回结果的请求"。它是**提交给一个系统的主张,而那个系统不管回执
有没有回来都会去执行它**。

三种结局,而第三种才是要害:

- **接受** —— 交易所说是,并给了它一个编号。
- **拒绝** —— 交易所说不,并说了原因。单子不存在,这是干净的终局。
- **未知** —— 超时、断连、或回复读不出来。**单子可能存在,也可能不存在。**

把第三种折进"错误",正是产生重复仓位的那个缺陷。超时后重试的调用方,有一半概率下了
两张单;放弃的调用方,有一半概率丢下了一张活单没人管。所以 `Unknown` 是**成功类型的
一个分支,不是错误**——编译器逼每个调用方对"不知道"做出决定。

怎么处理也不留给调用方judgment:**每张单都带一个发送前就选定的 client order id**,
所以"到底落没落"这个问题可以拿这个 id 去问交易所。交易所分配的 id 回答不了它——
问题的全部就在于交易所的回答没回来。

幂等在这里不是一个特性,而是这个设计成立的唯一理由。

## 接缝

`Execution` 是一个 trait,因为它背后的交易所会换,而它上面的层不能跟着换。行情侧已经
有这条接缝,第二个交易所接上去时采集程序一行没改。下单侧一条都没有——而风险登记表
写明了为什么这是更贵的那一半:**事故出在交易所边界的概率,远高于出在撮合内核。**

## 只读还剩下什么

`oq-gateway` 原本下不了单,而且第一行就写着这件事。这条性质现在是被**限定**,而不是被
放弃:

- 读账户依然不需要碰任何能交易的类型。
- 下单藏在 `Endpoint` 后面——一个只有两个值的类型,而 `Live` 必须被显式写出来。
  **配错的字符串不可能悄悄变成生产环境,因为根本没有字符串。**
- 每个下单方法都要求调用方传入 client order id,而不是替它生成——调用方不可能下出
  一张自己事后无法追问的单。

原来那条边界的意义是:交易应当是一个看得见的决定,而不是一次意外。类型化的 endpoint
加上强制的 client id,在让它能交易的同时保住了这一点。

## 每个箭头都会单独失败

| 失败 | 症状 | 应对 |
|---|---|---|
| POST 超时 | `Unknown` | 用 client order id 查 |
| 回复读不出来 | `Unknown` | 同上 |
| 流断开 | 收不到成交,账本开始漂移 | 重连,然后拿挂单和持仓与交易所对账 |
| listenKey 过期 | 流关闭 | 提前续期;过期要当成**缺口**而不是"安静" |
| 成交推两次 | 重复记账 | 按交易所 trade id 去重 |
| 成交乱序到达 | 仓位先变负再变回来 | 按交易所序号排,不按到达顺序 |

后三条正是为什么这条流被当作"**会有缺口的 feed**"而不是"可靠的日志"。采集那条路已经
学过这一课:一条安静了很久的流和一条已经死掉的流,从外面看是一样的,只有显式的存活
信号能把它们分开。

## 对账是常态,不是异常

框架不假定自己的账本是对的。持仓和挂单会定期、启动时、以及**任何一次 `Unknown` 之后**
拿去和交易所比对。`oq-gateway::reconcile` 已经在做这件比对,而且是**报告差异而不是
静默修复**——修错了比差异摆在那里更糟。

启动是最严格的一次:启动时发现一个自己不认识的仓位是**致命错误**,不是警告。一个在自己
不知道的仓位旁边开始交易的进程,它的风控限额没有任何意义。

## 还没有的东西

- 风控闸门本身(`oq-risk`):限额、kill switch、以及启动时"状态不明即致命"的检查。
- 通过 WebSocket 下单(交易所也提供)。先做 REST,是因为它的失败模式就是上面列的那些、
  已经被理解;在第一条写路径被证明之前加第二条,只会让面积翻倍而没有理由。
- Binance USD-M 以外的任何交易所。trait 存在的意义是让第二个成为"实现"而不是"重写",
  **但在第二个真的出现之前,这个说法未经证明。**
