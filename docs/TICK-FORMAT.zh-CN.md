# Tick 文件格式

> 状态：**v3 提案** · [English](TICK-FORMAT.md)
> 由 `oq-data` 实现 · 相关：[采集格式规范](CAPTURE-FORMAT.zh-CN.md) · [实施方案](IMPLEMENTATION.zh-CN.md)

回测读取的格式。它不同于采集归档（保存交易所原始字节），也不同于列式导出
（面向分析）。它存在的理由只有一个：让重放循环用最少的指令拿到下一条观测。

## 1. 它在体系里的位置，以及这为什么限住了变更风险

三种格式，三种职责：

| 格式 | 职责 | 能否重新生成？ |
|---|---|---|
| `.oqcap` | 原样采集。交易所字节，未经修改 | **不能。不可替代** |
| `.oqtk` | 归一化的引擎输入 | **能，从 `.oqcap` 重新导入** |
| Parquet | 分析与交换 | 能，按需导出 |

这个次序是整个设计**最重要的性质**。**tick 文件是派生物，不是归档。** 对它做
破坏性变更的代价是一次导入，不是数据丢失。真正不能不兼容变更的是 `.oqcap`，
它单独立规范，并且刻意保守。

**要维持这个性质。** 一旦有人把某份 `.oqtk` 当作某段数据的唯一副本，本文档的
风险评估就完全失效了。

## 2. 设计约束

1. **顺序扫描就是全部负载。** 回测读数百万条记录、每条几乎不做事，成本由拷贝
   次数和逐条解码开销主导。所以：定宽、小端、不按 schema 分支。
2. **两个时戳永远同行。** 为省 8 字节丢掉到达时戳，会让这份数据将来无法用于
   延迟感知的仿真，而这件事**事后不可逆**。所以它不是选项，也不是开关。
3. **字段只增不改**（D5）。格式必须让"加字段"变便宜——因为 v2 已经证明字段会
   增加：`volume` 就是那时加的。
4. **截断必须在分配内存之前被发现。** 因此 count 与校验和在头部，不在尾部。

## 3. v2 做对了什么，以及唯一没做对的地方

v2 是 32 字节头 + 64 字节记录（8 个 `i64`）。定宽、小端、正好一个 cache line、
双时戳强制——**这些都对**。

问题在于：**8 个字段正好填满 64 字节，加第 9 个字段就必须升版本并重写所有文件。**
从 v1 到 v2 已经加过一次，后面还会有——持仓量、序列号、资金费率。如果每加一个
字段都要付一次格式破坏加迁移，那就是**对"做正确的事"征税**。

v3 的存在就是为了取消这项税，并且**它应当是最后一次结构性变更**。

## 4. v3 布局

### 头部 —— 64 字节，正好一个 cache line

| 偏移 | 大小 | 字段 | 说明 |
|---|---|---|---|
| 0 | 4 | magic | `OQTK` |
| 4 | 2 | version | 3 |
| 6 | 2 | `header_len` | 64 |
| 8 | 2 | `record_len` | 每条记录字节数。**这就是可扩展机制** |
| 10 | 2 | `field_count` | `record_len / 8`，用于校验 |
| 12 | 4 | flags | 保留，必须为 0 |
| 16 | 8 | `record_count` | |
| 24 | 8 | `instrument` | 对本 crate 不透明 |
| 32 | 8 | `first_exch_ts` | 让目录工具无需扫描就能回答"哪个文件覆盖这一天" |
| 40 | 8 | `last_exch_ts` | |
| 48 | 4 | `crc32` | 记录区的校验 |
| 52 | 12 | 保留 | 必须为 0 |

### 记录 —— `record_len` 字节，全部为小端 `i64`

第 *k* 个字段永远位于偏移 `8k`。字段表是**全局的、只追加的**。

| # | 偏移 | 字段 | 起始版本 |
|---|---|---|---|
| 0 | 0 | 交易所时戳，纳秒 | v1 |
| 1 | 8 | 到达时戳，纳秒 | v1 |
| 2 | 16 | 最新价，ticks | v1 |
| 3 | 24 | 最高价，ticks | v1 |
| 4 | 32 | 最低价，ticks | v1 |
| 5 | 40 | 买一价，ticks | v1 |
| 6 | 48 | 卖一价，ticks | v1 |
| 7 | 56 | 累计成交量，lots | v2 |

### 零不是价格

写进记录的 `last` 永远不为零。其余价格字段用零表示"未知"，这一个不行——
内核不加守卫地把它当作标记价，而一个按"什么都不是"标记的持仓，在 1 倍及
以上杠杆下会爆仓，在此之下则让最低净值凭空少掉一整个持仓名义额。两个方向
都不出声。

没有价格的生产方不写记录。`oq-ingest` 在自身没有成交的窗口结转上一个价格，
首笔成交之前什么都不写。读的一方可以依赖这条；写的一方欠着这条。

这条是被量出来之后才成立的：一次 12 小时的实盘采集，56.4% 的 tick 带着
`last = 0`，只有 8.0% 三个价格齐全。

### 扩展规则

**新字段追加在末尾，`record_len` 随之增大。其他什么都不改，版本号也不动。**

读者用算术判断字段是否存在：当 `8 * (k + 1) <= record_len` 时字段 *k* 存在。
新代码读旧文件时，尾部字段视为缺失；旧代码读新文件时，忽略它不认识的那部分字节。

这就是 `record_len` 放在头部、而不是由版本号隐含的原因——它决定了"加一个字段"
是**一次迁移**还是**一次写入**。

有两条规则维持这个性质，且**没有例外**：

- **永不重排、永不改宽、永不复用既有字段。** 一个偏移不变而含义变了的字段，是
  电子交易史上若干最惨重事故的共同根因，而且**事后不可挽救**——因为旧文件和新
  文件无法区分。
- **版本号变动意味着不兼容变更**，而现在这件事应当永远不再需要。若有人提议升
  版本，举证责任在他：要说明为什么追加字段解决不了。

### 读取

两条路径，都正确：

- **零拷贝快路径。** 当 `record_len` 与读者自身的记录大小一致、且映射按 8 字节
  对齐时，记录区直接转成切片，无逐条开销。
- **逐字段路径。** 否则按固定偏移读取已知字段、跳过其余。每条多几次载入，换来
  **任何构建都能读任何文件**。

记录按 8 字节对齐。64 字节是甜点位（一个 cache line），但**不值得为了维持它而在
加字段时填充**——顺序扫描配合预取几乎察觉不到跨行，而这个格式只被顺序扫描，从不
随机访问。

## 5. 完整性与身份

两件不同的事，**刻意不合并**：

| 问题 | 机制 |
|---|---|
| 这些字节坏了吗？ | 头部 `crc32`，覆盖记录区 |
| 这些字节和之前是同一批吗？ | SHA-256，放在旁挂 manifest |

CRC-32 快、能查损坏，但**它不是内容身份**：把 parity 基线钉在 CRC 上，等于钉在
一个可能被碰撞的值上。身份用 SHA-256，与文件并列存放，沿用采集归档的 manifest
惯例：

```
ticks/<venue>/<symbol>/<YYYY-MM-DD>.oqtk
ticks/<venue>/<symbol>/<YYYY-MM-DD>.manifest.json
```

manifest 记录来源 `.oqcap` 文件、导入器版本与 commit、记录数与时间范围、以及
`sha256_raw`。最后这项就是 parity 基线所钉的东西（D13）——用同一个导入器重新
导入同一批采集会得到相同身份；而**换了导入器会表现为基线变化**，而不是变成一个
莫名其妙的行为差异。

## 6. 这个格式不是什么

- **不是归档。** 它是派生的。删了重新导入即可。
- **不是交换格式。** 那用 Parquet 导出。列式适合分析、不适合重放循环，想同时
  服务两者只会两边都做不好。
- **不自描述品种。** `instrument` 是不透明标识，到符号的映射属于数据目录，
  不属于每个文件的每条记录。
- **不压缩。** 引擎要热读它；压缩是拿扫描速度换磁盘，而磁盘是两者中更便宜的。
  要压就压采集归档——量在那边。

## 7. 列式导出

`oq-data` 可以把同一批 tick 写成 Parquet，位于可选的 `parquet` feature 之后。
这就是 §6 里那句"要交换格式就导出 Parquet"的兑现。

```text
cargo run -p oq-data --features parquet --bin oq-data -- ticks.oqtk --parquet out.parquet
```

八个 `Int64` 列——`exch_ts`、`local_ts`、`last`、`high`、`low`、`bid`、`ask`、
`volume`——zstd 压缩，合约 id 与 schema 版本写在文件的 key-value 元数据里，键为
`openquanter.instrument` 与 `openquanter.tick_schema`。

三个值得说明的决定，因为每一个都有一个显而易见的错误答案：

- **两个时戳都要，都不可选。** 两者之差就是 feed 延迟。只保留其中一个的导出，
  会让读者无法区分"feed 慢"和"行情慢"，而且这种损失是无声的。
- **整数，而不是缩放后的浮点。** 浮点列读起来更顺眼，但它是错的；scale 属于合约，
  不属于价格。文件精确往返，并有测试把每一列钉在 `Int64` 上。
- **feature 之所以可选，是因为依赖树约 90 个 crate**，比工作区其余部分加起来还多。
  `oq-data` 的默认构建仍然是零第三方依赖，CI 把 feature 构建单独作为一项检查。

在 7.3 小时实采的 BTC 永续数据上——262,365 个 tick——导出为 4.06 MB，原生格式
16.79 MB，即 24%，并且不需要自定义 reader 就能在 pandas 里读：

```python
df = pd.read_parquet("out.parquet")
latency_ms = (df.local_ts - df.exch_ts) / 1e6   # 中位 89.8，p99 102.1
```

校验和不跨格式携带。Parquet 有自己的页级完整性校验，而对我们已不再掌控的字节做出
断言是一个守不住的承诺；`read_parquet` 会重建 `TickStream`，由它重新计算校验和。
