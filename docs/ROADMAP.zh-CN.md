# OpenQuanter — 路线图

> 状态：**评审稿** · [English](ROADMAP.md)
> 配套文档：[为什么有 OpenQuanter](WHY.zh-CN.md) · [需求规格说明](REQUIREMENTS.zh-CN.md) · [实施方案](IMPLEMENTATION.zh-CN.md)

**所有里程碑最终服务于一件事**：回测与实盘之间的每一分差额，都说得清。
[为什么这是目标](WHY.zh-CN.md)、以及前身撞到什么才让它成为目标，是另一份文档；
这一份讲的是做事的顺序。

本路线图描述从项目当前状态到 2.0 的路径，以及此后的研究方向。它按
**里程碑**组织，而不是按日期。里程碑有**启动触发条件**与**验收门**：工作不因为
日历到了就开始，也不因为有人觉得差不多了就结束。

人周估算是小团队的指示性规划区间，已包含冗余系数。它们是估算，不是承诺。

---

## 指导原则

1. **先立锚点。** 确定性与 parity 工具优先于功能。没有它们，之后每一次改动都是
   在猜。
2. **保真度先于 AI。** 在低保真仿真器上做强化学习，等于教模型利用仿真器缺陷。
   AI 里程碑以保真度里程碑为前置。
3. **风险价值与性能价值同等重要。** 保证金建模的优先级高于提速工作，因为一个
   不会爆仓的回测，恰恰在最要命的地方是错的。
4. **昂贵的部分用触发制，不用排期制。** 实盘、高频保真、AI 扩展各自带明确的
   启动条件；条件不满足，里程碑就不启动。
5. **数据有时效，代码没有。** 没采到的那一天行情永久缺失。因此采集基建从 M0
   就开始，早于消费它的代码存在。

## 里程碑总览

| 里程碑 | 主题 | 累计人周 | 状态 |
|---|---|---|---|
| **M0** | 地基：仓库、采集、统计 | 3–6 pw | 基本落地 |
| **M1** | 确定性内核、L0 引擎、保证金骨架 → 首个预览版 | 15–27 pw | 大部分已落地 |
| **M2** | Python tier、保证金保真报告、研究工作流 → beta | 24–41 pw | **大部分已建成。G3 与 G7 的 parity 那一半现已测量而非卡住——两者都没通过，且差距都写明了。G11 已撤销** |
| **M3** | 实盘：网关、风控闸门、对账 | 39–62 pw | **范围内大部分已建成，准入条件仍一条未满足** |
| **M4** | 高频保真：L1 排队/延迟、L2 订单簿重建 | 54–83 pw | 已触发，且比“L1 第一版已存在”走得更远：L1 已建成，延迟按分布建模；L2 从重建出的订单簿里同时量排队位置和吃单者的行走；一次回测已经能从采集下来的归档抵达它。剩下的是拿录到的成交做校准——它卡在 M3 触发条件所要的那批成交上——以及既定顺序排在校准之后的概率化排队模型 |
| **M5** | AI 扩展：推理、RL 环境、特征层 | 62–97 pw | 触发制 |
| **2.0** | API 稳定化与语义化版本 | — | M3 完成且有外部采用之后 |

M0 与 M1 标"落地"指**范围内多数已建成并有测试**，不等于验收门已通过。截至最近
一次修订：确定性内核、L0 撮合、保证金叠加层、回测宿主、parity 工具、采集工具、
过拟合统计均已就位且全绿，`criterion` 基准也已建成，并在 CI 中设了吞吐下限。
M1 验收门上仍未达成的是：对参考实现的逐笔 parity——接近但**尚未通过，而差一点
的门就是没过**。常驻采集此后已连续运行超过一天,覆盖两个交易所 23 条流、归档零失败——这已经过了试采,但还没到出口门:出口门要的是**实测的** gap 率和有记录的存储增长,而现在有的只是一个运行时长。已建/未建的划分见 README。

M1 里有一项是**刻意做小的**。基准这个 CI job 断言的是**下限**，不是被跟踪的
基线：共享 runner 的性能在不同时段能差好几倍，严格比较会因噪声而误报，然后在
一周内被关掉。下限能抓住的是"引擎慢了一个数量级"这类真实会发生的回退。要精确
比较两个版本，是在同一台机器上本地跑 `cargo bench`。这是对原计划的修改，在此
记录，而不是悄悄放弃。

**M3 在四个准入条件一条都没满足的情况下,被建到了约一半的范围。这是对本文档自身
纪律的背离,不是对它的修订。** 网关会下单、会读用户流;风控闸门有 kill switch 和致命
启动检查;`oq-live` 把它们装成一个进程,而这个进程已经在 testnet 上真下过一张单又撤掉,
两次都在账户流上得到确认。而 M3 的四个条件——公开发布满六个月、一次差异全部归因的
影子跑、两次演练成功的带仓位切换、一个外部用户——**一个都没发生**。

记在这里,是因为本页开头第 4 条原则写着"昂贵的部分用触发制,不用排期制",而这就是
不遵守它的样子。**已完成的工作不浪费,也不回退**;代价在于:那个排序本来是用来保证
昂贵的那一半是**对着证据**建的,而它是对着热情建的。

M3 仍未建的部分,所以"一半"是个数字而不是感觉:`oq-live` 的快照恢复与优雅重启
(**在注释里有,在函数里没有**)、连接器一致性套件、第二个执行侧交易所、任何形式的
可观测性、实盘/回测差额归因、`oq-sim`、以及带仓位切换手册。

**G6 已经测了一半,缺的是区间的终点而不是起点。** 它要的是"从 journal 写入到
socket 写入"的 p99 延迟。近端已经有了——实盘路径在 `record.rs` 里落 journal,内核
也在这条路径上,由 `books.rs` 记账——而且 `oq-live` 每次运行的收尾都会报出它能看到
的那一段:journal flush 到调用客户端。远端没有:HTTP 客户端不暴露"字节何时进了
socket",所以打印出来的是一个**下界**,并且被明确标注为"不是 G6 的数"。要关掉这道
门,需要一个会报告自己写入时刻的客户端,或者一次在进程之外做的测量。

"已承诺"指当前默认计划。"触发制"指该里程碑有下文写明的启动条件，条件满足前
不会开工。

在等这个项目拿不到的输入,后者是还没写。

| 门 | **G7 改造后重过 parity** | **一半达成，一半得到了否定的答案。**模式那半已达成并有测试。parity 那半不再与 G3 同一阻塞，而跑了之后拿到的是结果而不是通过:大到足以达到 G3 吞吐的批，不保持成交序列——因为一批的订单是在批末提交的。`compare_modes` 报告分歧而不断言没有分歧，这个形状是对的——但这说明目标本身要的两件事互相拉扯，而这个取舍应该写进目标里，而不是靠跑一遍去发现 |
| 门 | ~~**G11 外部冷启动 ≤30 分钟**~~ | **已撤销**——理由见 [REQUIREMENTS](REQUIREMENTS.zh-CN.md)。它走之前确实留下过一个真发现:快速上手的第一条指令是 `cargo install oq-cli`,而已发布的 `oq-*` 全是 `0.0.1` 占位包,照做的人会在第一分钟断在一个与他毫无关系的地方。那是靠设想一个外人会撞上什么而发现的,并当作 bug 修掉——这才是这类事情该有的形态 |

| L2 | 订单簿重建、快照对账、gap 处理 | 重建已建成,并且**在真实归档上测过**:133,910 条深度更新、0 序列错误、0 gap、0 交叉盘口、最深 10,286 档——`RECONSTRUCTS CLEANLY`。**买卖两侧现在都从它测量。** `L2Engine` 读订单加入的那一档实际挂出的量,取代 L1 假设的 `QueueAhead`;吃单则逐档走完盘口,取代 L1 的平方根惩罚。实测**替代** policy 而不与之叠加,盘口够不到的那笔单保留 policy,`swept` / `unswept` 报告一次运行到底是被哪一个定的价。同一次观测里的多笔吃单消耗同一份深度副本,所以第二笔的规模不是免费的。盘口与 tick 冲突时取更差的价,以保持挡位的单调。任何 MBP 行情都无法区分排在你前面的撤单与排在你后面的,所以队列只随成交递减,按构造是保守的。**回测现在能用到它了**:`RunConfig::at_tier` 选择档位,`run_observations` 接收同一条流上的 tick 与深度,`book_tiers` 是那个对比——没给深度的 L2 逐比特重现 L0,被告知「假设前面 64 手」的 L1 与看到 64 手盘口的 L2 成交数完全一致,而从 16 手到 64 手,一个挂单策略的大部分就不存在了。还差两处:把归档转成这条流目前是调用方自己写的循环、不是一条命令;深度不走 `Event`,所以一次 L2 运行的日志能重放它的订单,重放不了它撮合时的那本簿 |
| 验证 | 风格化事实测试集 | 对生成行情已建成,**现在也在真实行情上测过了**。`oq-data` 会为任意 tick 文件报出这四条事实,所以这个对比现在是一条命令而不是一项研究:四天采集的 BTCUSDT(1590 万笔成交折出 5,759 个一分钟收益率)每天四条成立三条,超额峰度 8–11,而夹具是 0.03 / 0.07 / −0.05。更要紧的发现是这个结论有多容易被推翻——四天合并算,峰度 951 且 ρ(1) 不成立;从 5,759 个收益率里去掉**两个**(一分钟涨 4.1%、成交量是中位数的 251 倍,加上它的回落),就变成 24.6 且 ρ(1) 成立。短样本的判定就是它最大那次事件的判定,这正是它只能是测量、不能做门禁的原因。**订单流自相关已建成**，而订单流原来就在归档里——交易所会发布是哪一方越过价差，只是没有任何适配器读过它。`oq-trade-check` 会报告它，`conformance` 要求每个适配器都解析它，而这次测量逼出了一个区分：在原始**成交**上，一小时 BTCUSDT 的 lag-1 系数是 0.83、最长同向连续 3,335 笔——那 3,335 笔只跨了 14 毫秒，是一笔单吃穿三千个挂单，而不是三千个决策。折叠成**订单**之后（`as_orders`），179,547 笔成交变成 39,019 个订单，lag-1 是 **0.19**，缓慢衰减，与已发表的数字吻合。两者都报告：原始序列是队列真正面对的，折叠后的才是文献所指的 |
| L2 | **把归档转成一次运行的输入** | 已建成——`fold_into_observations` 按交易所产生的顺序把 tick 与深度交错起来，`oq-tiers` 就是那条命令：一个策略、一份归档、两个档位。在跨四天、十个时段的采集数据上（130 万条深度更新，**零拒绝**），一张挂在盘口最优价的买单在 L0 成交 13,972 次、L2 成交 3,140 次——**回测里 77.5% 的成交是队列根本没排到的交易**，而且没有哪个小时保留超过 44.6%、也没有低于 12.5%。簿是从第一条更新自举的、不是 REST 快照（归档里没有），所以早期读到的队列比实际短 |
| L2 | **深度进日志** | 已建成——`Event::Depth` 是 kind 9，也是这个模式里第一个变长载荷，自带档位计数，好让 decode 能拒绝与之不符的正文。有一个测试重放一次 L2 运行、把输出与状态和实况运行对比，若深度被丢掉它就失败。`Event` 因此失去 `Copy`——一列档位不可能是 `Copy`。代价是日志体积：采集到的一小时单个合约就有十万多条更新，所以不读深度的运行不该被喂给任何深度 |
| 验证 | L0 / L0+margin / L1 对比报告 | 已建成，且现在也覆盖 L2。`tiers` 对比 L0、L0+margin 与 L1，并显示这些档位**并非**按悲观程度排序。`book_tiers` 在一组不同厚度的生成盘口上加入了 L2——没有被喂过深度的 L2 逐比特重现 L0，而被告知「假设前面 64 手」的 L1 与看到 64 手盘口的 L2 成交数完全一致。`oq-tiers` 用采集到的归档跑同一个对比，77.5% 那个数字就是从那里来的 |

## M2 — Python tier、保证金保真、研究工作流

**启动条件。** M1 验收门通过。

**范围。**

- `oq-py`：兼容模式正式化；达速模式设计并实现（订阅粒度、批量回调、状态镜像）。
  批处理不是免费的，而且代价没有被藏起来：每 `n` 个 tick 才被调用一次的策略，
  无法在这一批的第 1..n-1 个 tick 上动作，因此它的决策最多迟 `n - 1` 个 tick。
  `batch=1` 就是兼容模式，并有测试断言两者完全一致；`n > 1` 时的偏离由
  `compare_modes` **实测**，而不是假定它很小。在示例 crossover 策略上，
  `n = 64` 吃掉 18% 的收益，`n = 512` 则把收益完全抹掉。
  它换来的东西也被实测了，因为只报价格不报货物不算一笔交易：在 20 万个 tick 上
  用一个什么都不做的策略测，达速模式最高约为兼容模式的 7 倍。batch=8 用 1.3%
  的收益换 2.8 倍，batch=64 用 18% 换 5.8 倍，batch=512 换 6.9 倍但收益归零。
  哪一档可以接受取决于策略本身，所以绑定层只负责测量，不替人选。
- **保证金保真报告（G5）。** 在开/关保证金两种模式下复算历史极端行情窗口，并
  公开**尾部偏差报告**的方法论，已发表于
  [MARGIN-FIDELITY.zh-CN.md](MARGIN-FIDELITY.zh-CN.md)。对杠杆策略而言，这是整个计划中价值最高的单一
  交付物：它量化了无保证金回测究竟乐观了多少。
- `oq-data`：双时戳 Arrow/Parquet 层、双时间参考数据、严格 as-of join 工具；
  `oq-features` 骨架——一个定义、
  两条由它派生（而非各写一遍）的执行路径，以及一个针对四类经典漂移方式做过测试
  的一致性指标。
- `oq-cli`：已交付 `data`、`replay` 与 `parity` 子命令；集成 `oq-stats` 使扫描
  默认输出 DSR/PBO。`parity` 此前被记为**不会再写**，理由是 `compare` 需要
  `RunManifest` 与 `RunOutput` 而两者都没有序列化格式。那个判断是诚实的，但它把
  错的东西说成了不可能：真正缺的是**文件格式**，`oq_parity::wire` 就是它，格式
  一到位，子命令一个下午就写完了。`backtest` 与 `sweep` 仍然不做，原因来自设计
  本身而非进度：策略是编译进二进制的 Rust 代码，没有任何参数能指名一个策略，
  子命令只会是一个更差的 `cargo run --example`。`oq` 在被问到这两个命令时会说明
  原因，而不是报“未知命令”。
- **采用就绪度：** 快速上手文档、至少两个示例策略、带 golden 测试的样例数据集。
  三项都已具备。这里原本的第四项是一次由外人完成的计时冷启动，`G11` 已撤销，
  理由见 [REQUIREMENTS](REQUIREMENTS.zh-CN.md)。

- **保真度报告（FR-MATCH-3、FR-MATCH-4）。** `oq_backtest::validity` 报告参与率、
  maker/taker 拆分、该档位对延迟与冲击的假设，以及——在运行主动要求时——峰值保证金
  占用与最接近强平的距离；当峰值参与率说明这次运行replay 了一个它本会推动的市场时，
  给出标记。

  两个诚实的边界。它是一次**调用**而不是一个字段：`report(&result, &ticks, …)`
  需要 tick 序列，而流式运行已经把它消费掉了，所以"每次回测都产出保真度报告"是靠
  "它是一行、无需配置"来满足的，而不是靠它自动发生——这是更弱的保证，并如实写在
  这里。保证金追踪是**可选**的，因为测它要花掉引擎约五分之一的吞吐，而且它不能采样：
  要的是极值，而一个错过了最接近点的"最接近距离"比没有更糟。没有要求追踪的运行报告
  `NotTracked`，绝不报零。

**验收门。**

- **G3** 吞吐与 **G4** 扫描目标达成。G4 已达标并由 CI 检查：
  `cargo run --release -p oq-examples --example sweep_100`——100 个配置、每个
  60 万 tick、含 DSR 与 PBO，在开发机上耗时 2.65 秒，预算 1800 秒。G3 仍需要它
  所依据的达速模式，以及在同一台机器上跑一次前代作为对照。
- **G5** 保证金保真验证通过；尾部偏差方法论公开。**已达成。**见
  [MARGIN-FIDELITY.zh-CN.md](MARGIN-FIDELITY.zh-CN.md)，工具在
  `oq_backtest::fidelity`，研究在 `examples/margin_fidelity`。
- **G7** —— 策略在兼容模式下零改动运行；改造为达速模式后重新通过 parity。
  **达成一半。** 模式这一半已完成并有测试：一个不含框架痕迹的策略在兼容模式下
  运行，改造为达速模式只是改一个方法，而 `compare_modes` **断言** `batch=1`
  产出完全一致的运行——不是由文档来断言。重新通过 *parity* 指的是对前代基准，
  与 G3 是同一个阻塞点。
- ~~**G11** 初验~~ —— **已撤销**，不是延后。给第一次回测掐表，测的是错的东西：
  值得用的工具，值三十分钟以上；不值得用的，一分钟也不值。而且它用的仪器也不
  成立——一个读者的实测是 n=1，因人、因机器而异的程度大过这里能控制的任何因素。
  这个目标真正想要的东西是真的，并且作为普通工作保留下来：快速上手、五个示例、
  golden 测试都在，而一条跑不通的文档命令是发现即修的 bug，不是一道会挂掉的门。
- **Beta 发布**，API 已文档化但仍不稳定。

**这两个门已经跑过了，结果不是"通过"。** G3 与 G7 的 parity 那一半，此前都卡在
"要在同一台机器上跑一遍闭源前代、跨多年窗口"。那一步做完了，于是它们从"卡住"
变成了"测过、未达标"：

- G3 是 **7.13×，目标 8×，差 12%**。差距的位置也测出来了：批大小超过 512 之后
  不再改善、到 4096 反而更慢，所以剩下的不在跨语言边界上，而在引擎内部。这比
  "卡住"有用，因为它指向要改哪里。
- G7 的 parity 那一半拿到的是**否定的答案**，不是没答案：一批的订单在批末提交，
  所以大到能达到 G3 吞吐的批，必然改变成交序列。目标要的两件事互相拉扯，这一点
  应该写进目标本身。
- 本项目自己采集的数据仍然是七个日历日（2026-08-15 到 2026-08-21，其中五天完整）。
  上面那次测量用的不是它，而是公开的交易所成交归档，两边引擎读同一份。

**已经测到的**，并且以它自己的名义（而不是 G3 的名义）记录：Python 层的达速
模式在 20 万个 tick 上最高约为其兼容模式的 7 倍。那是另一个比较——一个绑定对
另一个绑定，而不是这个引擎对一个解释型实现——上面已按其本来面目记录。

## M3 — 实盘交易

**启动触发条件（全部满足）：**

1. 公开内核已发布 ≥ 6 个月且无未决 P0/P1 缺陷。
2. 有策略以影子模式对着真实交易所跑了足够长的时间可供比对，且影子运行与交易所
   之间的每一处分歧都被**归因**，而不是被容忍。
3. 带仓切换流程已在测试网成功演练至少两次。
4. 至少有一个真实的第三方用户在使用本框架——对小团队而言，外部使用是唯一诚实
   的质量信号。

**范围。** 人周刻意向连接与对账倾斜，而非内核：在这类系统中，事故绝大多数发生
在交易所边界与状态对账层，而不是撮合内核。

- `oq-gateway`：参考永续适配器——行情、下单、用户流——并把**对账作为一等设计
  对象**：回报丢失、重复、乱序的完整处理路径。外加连接器一致性测试套件。
- 按同一契约实现更多交易所适配器。
- `oq-risk`：RiskGate，含盘前检查、kill switch、启动对账与"未知状态即致命"语义。
- `oq-live`：进程装配、快照恢复、平滑重启、每账户一进程。
- 可观测性：在定义好的测量边界埋延迟直方图、结构化指标、告警接入钩子。
- **实盘与回测差额的归因。** 上面的进入条件和出口门都要求"每一处背离都必须被归因，
  而不是被容忍"，而这份归因长期没有任何东西产出——需求写下了
  标准，却没有指定仪器。**那件仪器现在存在了**：`oq_parity::attribution` 把差额拆成
  滑点、排队位置、资金费与模型的偏差、延迟、手续费档位，拆不动的部分报告为
  **未解释残差**。差额取自两个独立来源（交易所的已实现盈亏与内核的），组件另行计算，
  所以残差是**减出来的而不是凑出来的**——有测试故意把某个成因算错，断言误差落进残差。它的第一个前置条件——实盘进程记录决策 journal
  ——**已经满足**：`oq-live` 现在依赖 `oq-journal` 并在 `record.rs` 里落盘。第二个
  **在内核这一层已经满足**：`oq-live` 现在依赖 `oq-core` 与 `oq-margin`；
  `oq_live::shadow` 把回测所用的那同一个 `Kernel` 跑在实盘 session 旁边，以四种
  具名形态外加一项持仓比对报告它与交易所的分歧，并通过 `Shadow::evidence` 把它交给
  `oq_parity::attribution`——那是本项目头号主张里最后一处没接上的缝：shadow 产出
  分歧，分解器要的是证据，而没有任何东西把一个变成另一个。资金费与手续费是它的
  **参数**而不是字段，因为 shadow 看不到它们：传 `None` 就是说"没人读过交易所的
  对账单"，报告随之拒绝给出残差，而不是报出一个由没人测量过的成因所解释的差额。

  而 `oq_core::Matching` 补上了缺失的另一半。内核现在可以接受**由交易所决定**的成交，而不是自己产生成交，且
  记账完全相同——有测试断言同一笔交易用两种方式入账后，持仓、均价、手续费、余额
  与权益全都一致。这就是让 §1 那句"回测与实盘只差事件生产者"从愿望变成事实的
  东西：账本只有一份实现，变的只是成交的来源。

  两条拒绝把它撑住。在 `Matching::Venue` 下撮合器绝不成交，因为一个既撮合又接受
  交易所成交的内核会把每笔交易记两遍，而第二份看起来和第一份一模一样。反过来，
  一笔交易所成交到达 `Simulated` 内核时会被拒绝而不是被应用，因为模拟运行自己
  产生成交。成交后订单还会离开簿子——这一条针对的是**重放**而不是实盘运行：一份
  同时含有下单和交易所成交的 journal，被一个没设置模式的构建重放时，会把订单挂上
  去然后再撮合一次。

  剩下的是装配——`oq-live` 还不是以 `Venue` 模式的内核**驱动自己**，它是在旁边
  观察一个内核。内核已经就绪，进程还没有。
- `oq-sim` 全量：整个场景目录 + 网关 fuzz（断连、乱序、重复、部分成交）。
  **网关这一半已存在** —— `oq-live` 的 `gateway_fuzz` 用目录里的每一个场景驱动实盘
  账本，断言的是**不变量而不是输出**：同一笔交易被记两次只应移动账户一次；报告乱序
  不改变账户最终落点；丢失的报告会留下一处由对账器点名的分歧；交易所发什么都不能
  让账本凭空产生成交。

  它第一次跑就抓到一个。账本没有去重——订单跟踪器有，而后来加的内核账本没有，这正是
  同一件事在两个时间被实现在两个地方时会裂开的缝。一笔重投的成交会让持仓翻倍，而
  重连后的流重复自己是常规而非异常。
- **带仓切换 playbook**，端到端演练通过。
  预案本身已经写出——[CUTOVER.zh-CN.md](CUTOVER.zh-CN.md)——并且明确写着它是骨架：
  每一步都已明确、每条命令都真实存在，而一次都没有演练过。第 6 节列出在能开始
  演练之前还缺什么，第 7 节写明每次演练必须产出什么。

**验收门。**

- **G6** 延迟目标在定义边界上达成。
- 影子运行一致率达标，每一处分歧都有归因。
- 全场景目录在 fuzz 下通过。
- 灰度上线稳定运行 ≥ 2 周。

## M4 — 高频保真

**启动触发条件（两条都满足）：**

1. 存在具体的（而非假设的）做市或高频策略候选，且其 edge 受仿真保真度限制。
2. 已积累**足够回答当前问题**的增量深度数据。**不是一个固定的月数**——原文
   写的是"至少 6 个月",而仓库里找不到任何论证:那个数字只出现过一次,旁边
   是一条无关的"内核发布满 6 个月"。L2 需要多少数据,取决于拿它回答什么:

   | 要回答 | 需要 | 理由 |
   |---|---|---|
   | 撮合器能否重建并撮合 | 几天 | 只需证明序列号、gap、快照对账在真实数据上成立 |
   | 排队模型是否已校准 | 几周 | 需覆盖不同流动性状态,不需要跨季节 |
   | 做市策略的边缘是否成立 | 数月 | 这一档才是"多月窗口"真正的论据所在 |
   | 结果是否统计显著 | 更久 | 而本项目的立场恰恰是"一次运行不构成证据" |

   只有第三档曾经等于六个月。前两档现在就可达——而在归档拉取部署之前,它们
   因为另一个原因不可达:暂存桶 7 天过期,保留窗口有硬上限,采多久都没用。

**范围。**

- **L1**：**第一版已存在** —— `oq_engine::l1` 建模了排队位置、入场与回报两段延迟、
  以及平方根 taker 冲击罚项；参与率告警已随 M2 的保真度报告落地。剩下的正是这个
  里程碑真正要做的事：**校准**。模型接受一份 `Policy` 假设，因为 tick 格式既不携带
  订单簿深度、也不携带本部署真实的延迟；把这些假设变成测量，需要进入触发条件所要求
  的那份真实成交记录。另有三块未做：概率排队档（已交付的是保守档，这正是既定顺序）、
  用**分布**而非常数表示延迟、以及 **feed 延迟**——它是事件生产者的属性而不是撮合器的，
  属于宿主循环；把它也放进引擎会让同一个事件被延迟两次。
- **L2**：由增量深度重建订单簿并在其上撮合，配快照对账与 gap 处理。
- 风格化事实测试集进 CI（厚尾、波动率聚集、订单流自相关），验证仿真器行为像
  一个真实市场。
- 同一策略在 L0 / L0+margin / L1 三档的对比报告。

**验收门。** **G8** 达成，外加一份对比模型预测成交概率与真实成交的校准报告。

## M5 — AI 扩展

各组件独立触发。

| 组件 | 启动触发条件 | 交付内容 |
|---|---|---|
| `oq-infer` | 有训练好的模型要进入回路 | 进程内 ONNX 与编译树推理、预热与固定形状、Python/Rust 预测 parity 门（**G9**） |
| `oq-env` | ~~L1 保真度达成（M4）~~ —— **已触发并建成** | 控制反转的 gym 式环境 + 原生向量化批处理，seed 贯穿每个随机源（**G10**） |
| `oq-features` | 随 `oq-infer` 一同 | PIT 特征层，研究与实盘共用一条代码路径，线上/线下一致性度量 |
| `oq-lab` | 仅时间盒探索 | LLM 沙盒，配类型化只读工具 API 与审计日志。无验收目标，无兼容承诺 |

**关于 `oq-lab`。** LLM 驱动策略发现的公开证据很弱：对该领域文献的可复现性审计
几乎找不到能复现的结果，而且模型训练数据通常已经"见过"被评估的回测窗口。我们
保留这个实验沙盒，因为工具成本低、期权价值真实；我们把它标为实验性，因为假装
不是这样是不诚实的。评估只使用模型训练截止日之后的数据。

## 通往 2.0

2.0 是一项 **API 稳定承诺**，不是功能数量的门槛。它要求：

- M3 完成，且框架在维护者机器之外的地方跑实盘。
- 公开 crate API 与 Python 绑定面经过稳定性评审；已知设计错误在冻结**之前**改掉。
- 事件 schema 版本化，并有文档化的演进政策（只加字段，永不复用字段）。
- 连接器契约的文档化程度足以让第三方在不阅读适配器内部实现的情况下写出适配器。
- 文档覆盖快速上手、架构、保真度语义、保证金语义与运维。
- 自此严格执行语义化版本。

## 风险清单

| 风险 | 等级 | 缓解措施 |
|---|---|---|
| 实现过程中 L0 语义走样 | 高 | parity 工具先行；每一处差异都归因，不放行任何一条 |
| 保证金规则复现错误（分级表、全仓细节） | 高 | 规则双时间存储；与交易所强平计算器抽样核对；单调性属性测试 |
| 达速模式改造引入行为漂移 | 高 | 达速模式独立重新通过 parity 门 |
| PyO3 回调开销主导 Python tier | 中 | **降级,而且理由来自外部**:这条是在有全局解释器锁的世界里写的。PyO3 v0.28 支持自由线程 Python 3.14 与 GIL 释放 API,不持有共享 Python 状态的模块可以标 `gil_used = false` 而无需重新启用锁。双模式设计仍然隔离风险、兼容模式仍然不承诺速度,但这个问题现在是**要去测量的**而不是要绕开设计的。见 D16 |
| 采集基建规模不足（流量、gap、成本） | 中高 | 专用采集机 + 本地存储 + 批量归档；先做 7 天试采实测流量、gap 率与成本再定 |
| L1 校准数据不足 | 中 | 采集从 M0 开始；数据足够之前只启用保守排队档 |
| 类型系统分裂成 Rust 与 Python 两种方言 | 中 | 单一类型系统铁律；绑定暴露同一套类型，绝不搞平行模型 |
| Rust 内核沦为某个 Python 库的实现细节 | 中 | 引擎必须在没有任何解释器在场的情况下可构建、可测试。**这是强制的而不是意愿**:per-crate 依赖预算把 12 个 crate 钉在零,组合性检查逐个单独构建每个 crate |
| 范围膨胀 | 高 | 承诺范围止于 M2，之后一律触发制 |
| 专有内容泄漏进公开仓库 | 高 | 全新 git 历史；CI 秘密与模式扫描；专有内容只存私有 overlay；发布前人工审计 |
| bus factor = 1 | 中高 | 面向 agent 的代码库（每 crate `AGENTS.md`、分层验证锚）；行为以确定性测试固化；设计理由全部落纸，不留脑内 |
| 把"做完框架"当成目标本身 | 高 | 每个里程碑写明它解锁什么能力；每道门都问一次"到底什么被可度量地改善了" |
| 执行接缝的第二个实现，签名那一半还没跑过 | 中 | 原本是:根本没有接缝。`Execution` 现已存在，`oq-gateway` 为两个交易所实现了它，上面的层不再点名任何一家。两侧现在都有各自适配器能通过的一致性测试——用各自提供的报文驱动，所以每一套测的都是契约本身，而不是某一家的字节;行情那一套在第一次跑的时候就抓出了一条写错的约定，下单那一套之所以存在，是因为 Binance 用 HTTP 状态码回答拒单、OKX 把拒单包在 200 里，照着前者写的分类器会把后者的每一次拒单都标错。剩下的比整条接缝要窄:OKX 的签名那一半需要凭证和一个真实账户才能跑，在那之前，第二个实现只在不需要签名的那一半上被验证过 |
| ~~品种模型裂成两半，且两半都不在内核~~ | 部分关闭 | **身份与精度那一半已经做完。**`oq_types::Instrument` 就在内核里，携带价格与数量的小数位、合约乘数、价格与数量网格、以及交易所的最小名义额；`oq_margin::Contract::of` 从它派生出经济属性，而不是另写一份——所以一个手写的 `tick_cash` 不会在重新上市改了精度之后与定义悄悄分家。`oq-l2feed` 里那第二份已经不存在了。**币种那一半现在关掉了一半。** `Currency` 是一个代码，`Balances` 是一个账户按币种持有的东西，`State` 持有一份——所以一本**结算**在多种货币里的账现在可以表达了：一笔以账户不结算的币种收到的款项会被持有并报告，而不是按隐含汇率 1 折算掉、或者干脆丢掉。仍然未决的是**跨币种合计**，那需要一个汇率来源、以及某个汇率成立的那一刻；在那之前，一个账户可以持有多种货币，而权益只在它结算的那一种里计算。`Cash` 本身没有变，而且是刻意的——币种属于槽位，就像标的属于一本簿、而不属于每一个价格 |
| `Strategy` 定义在回测宿主里 | 中高 | 实盘要么依赖 `oq-backtest`，要么另起一套策略 trait，无论哪种 G7（同一策略不改代码跑两种模式）都不成立。趁外部代码还没实现它，把 trait 挪到两个宿主之下 |
| ~~L0 被冻结为回归锚点，且撮合没有接缝~~ | 已关闭 | 对 L1 而言，用一种不需要本条所建议的重构的方式解决了。`L1Engine` **拥有**一个 `L0Engine` 且从不修改它——订单在没有资格进入之前被挡在外面，成交在它产出之后再做调整。所以 L0 不需要接缝、不需要 trait、根本没有改动；并有测试断言透明 L1 策略产出与 L0 逐比特相同的成交。L2 可能仍然需要接缝；L1 证明了先试「包一层」是够用的 |


最后四条不是假设。它们是拿代码对照本计划读出来的、当下就存在的结构性缺口，而且
形状一致：现在补都便宜，之后每多一个依赖现状的 crate、绑定或外部实现，就贵一分。
把它们记在风险清单而不是 issue 里，是因为"这件事以后要付多少代价"本来就是这张表
在问的问题。
